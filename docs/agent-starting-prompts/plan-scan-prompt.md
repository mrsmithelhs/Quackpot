# Plan Scan Prompt

Audit the development packets in `docs/development/` against reality and report discrepancies. You are producing a **triage report for the orchestrator**, returned as thread output; you write no file and do not change any packet's status yourself (implementers never set status; see `AGENTS.md` guardrails).

## If the status tool exists, start there

If `scripts/dev/plan-status.js` exists, run `node scripts/dev/plan-status.js lint` and `... list` first and treat their output as the baseline; your job is then to verify the *flagged* items and spot-check the rest.

## Evidence hierarchy (strongest to weakest)

No single location is "the real indicator." Weigh evidence in this order, and when layers disagree, report the disagreement rather than picking silently:

1. **Repository reality** — does the code/content/data the packet promised actually exist and work? (e.g. the module it says it created, the behavior its validation checklist describes). This outranks every label.
2. **Git log** — commits referencing the plan id and whether the packet's expected artifacts appear in history.
3. **Progress report content** — `reports/development/<packet-folder>/progress.md`: what it claims was done and its "ready for review" line. A report existing does NOT mean complete; a missing report does not always mean undone.
4. **Packet frontmatter** — the `status:` field.
5. **README index row** — `docs/development/README.md`. If the index is generated by the status tool, skip comparing it; if hand-maintained, treat disagreement with frontmatter as a finding.

## Known failure modes to look for

- **Stale-ready / superseded-in-fact:** a packet still marked `ready` whose work was absorbed by later packets. Handing it to an implementer would redo finished work. Flag as `recommend: superseded-by <ids>`.
- **Ran-but-never-closed:** a packet marked `draft`/`ready` whose outputs clearly exist or whose findings later packets consumed. Flag as `recommend: complete` or `recommend: needs orchestrator close-out`.
- **Intentionally-not-doing vs. forgotten:** blocked stubs and deferred work — check whether the packet says WHY it's parked. If the rationale is recorded, it's healthy; if absent, flag for an explicit `parked` + `resolution`.
- **Delivered-but-unreviewed:** implementer report says done, packet still says `in-progress`/`ready` — the orchestrator review handshake never happened.
- **Contradictory closure signals:** packet says `complete`, but its validation checklist items are unchecked, or its promised artifacts are missing, or the decision log records a reversal it doesn't reflect.

## Output format

A single markdown report with:

1. **Discrepancy table** — one row per flagged packet: `id | status | report evidence | git evidence | what's wrong | recommended status + one-line rationale`.
2. **Healthy summary** — count of packets where all layers agree (don't list them all).
3. **Dependency hazards** — any packet marked `ready` or `in-progress` whose `depends_on` packets are not complete.
4. **Suggested orchestrator actions** — the minimal set of status changes + `resolution` notes that would make the whole set consistent.

Do not edit any packet, the README index, or the decision log. Do not start implementing any plan you scan.
