## Pilot, validation and workflow proposal

Pilot two focused briefs under root clearance: one paid-vs-unpaid comparison and one pre-race/rest or exit/Receipt continuation. Demonstrate checkpoint load plus narrowly named next actions and state/log/UI evidence, protection of independent ordinary saves and rejection of stale/malformed inputs. Finite viewport/input budgets, no owner-profile writes, no actual learner data. Use isolated profiles, known loopback server ownership, bounded waits/output and cleanup; never kill unrelated processes. Existing one-game-source server can be reused only when verified and coordinated. Every executable batch is guarded and serialized, no full-suite/watcher/mutation sweep or installs by default. Root approves exact resource budget before runs.

Record setup effort/actions avoided and actual load/continuation behavior; do not invent a time-saving percentage. Stop at first validation failure for diagnosis. Browser feasibility/accessibility/device limits remain explicit. No reviewer swarm: first pilot by the single implementer, later root may authorize one small read-only reviewer assignment using one exact checkpoint and brief. Model/provider choice and budget remain separately approved; existing advisor declaration/routing still applies.

Propose a short optional workflow: relevant changed area -> named fresh checkpoint -> short brief and look-fors -> isolated bounded observation -> findings with fixture/source hashes -> root disposition. Preserve a full-start smoke path for appropriate integration changes; checkpoint tests are not proof of whole-run correctness. Do not insert this into global AGENTS or every packet until owner accepts pilot usefulness.
