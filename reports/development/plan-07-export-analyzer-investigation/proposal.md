The teacher selects multiple ZIP files for direct local browser analysis, with no extraction step, transmission, account, telemetry or external runtime resource. Keep imported data in memory initially; teacher-initiated CSV is a separate later addition requiring its own scope. Associate submissions through the assignment system, outside the payload.

| Teacher question | Candidate evidence / source | Privacy cost and limit |
|---|---|---|
| Can the file be interpreted? | Format, schema and content/catalog version; exporter metadata | Version may narrow a cohort; select only necessary metadata. Unknown versions are not silently interpreted. |
| Did this submitted run reach a Receipt? | Completeness status and terminal route, derived from terminal and Receipt evidence | Route reveals a choice; a Receipt is not proof of learning. An incomplete record is unknown, not failure. Immediate Uninstall is legitimate. |
| Which techniques were displayed? | Versioned technique IDs, derived from actual cue/offer/display records | Records exposure, not attention or influence; absence is unknown if evidence is incomplete. |
| What happened and in what order? | Bounded, meaningful ordered display and action/outcome timeline, projected from the relevant source events | More behavioral detail and linkability than a summary; select each category for a teacher question, exclude race frames, poses and internal-state noise. Sequence does not prove cause. Distinguish outcome committed from outcome actually displayed. |
| Is this a repeated export of a run? | Random per-run ID generated for a new run, persisted across that run's saves and re-exports | Pseudonymous and linkable across files, not a student or installation identity and not an authenticity proof. ID lifecycle, collision handling, restore and legacy cases need later design and tests. |
| Did submitted runs differ? | Teacher compares separately submitted run IDs, summaries and timeline evidence | Describes submitted runs only; cannot count all attempts, establish that one student made each file, or prove replay motive. Shared/cleared devices and selective submissions matter. |
| Did the cue affect the player? | Discussion question separate from observed display and action | Do not assert an answer; no reflection/free text exported by default. |

Default omission: student name, duck name, class code, arbitrary free text, reflection, persistent installation ID, seed and exact timestamps. Duck name is free text and can contain personal information; opt-in or default inclusion adds privacy cost without a settled teacher need. External assignment association avoids duplicating identity in the file, though the association itself remains identifying. Seed and reproducible reconstruction/checkpoint files are a separate purpose and future scope; do not treat a seed as identity or replay proof. Each proposed action or outcome field must carry a concrete teacher question, event source, completeness semantics and privacy rationale before adoption.

## ZIP technical investigation and bounded future spike

A ZIP archive is a container, not merely gzip-compressed JSON renamed `.zip`. The [WHATWG Compression Standard](https://compression.spec.whatwg.org/) defines compression streams such as gzip and deflate; those streams alone do not supply ZIP archive structure. ZIP creation and import therefore need an archive implementation or other separately verified local mechanism. No compression ratio, file size, performance or compatibility result has been measured for Quackpot.

The [fflate author documentation](https://github.com/101arrowz/fflate/blob/master/README.md) describes browser ZIP creation and streaming extraction. Its [UnzipFile API](https://github.com/101arrowz/fflate/blob/master/docs/interfaces/UnzipFile.md) says compressed and original sizes may be absent in streaming archives, and exposes chunk callbacks and termination. This makes counting **actual emitted bytes** necessary; claimed sizes alone are insufficient. [zip.js's ZipReader documentation](https://gildas-lormeau.github.io/zip.js/api/classes/ZipReader.html) describes reading the central directory and seekable Blob/range access. Both are candidates for evaluation, not selections, installs, proof of safe enforcement or offline compatibility. Check exact versions, licenses, dependency and worker behavior, browser compatibility, local bundling and no-network behavior in the later spike.

Future importer contract, to be established and measured with labelled synthetic data:

1. Set finite per-file compressed archive bytes, maximum member count, maximum actual expanded bytes per member and cumulative expanded bytes, and bounded total batch bytes/files, memory, work/time and concurrency. These are **required limits, not numerical decisions**: choose concrete constants in the spike based on representative use and device evidence. Count actual output while streaming; abort as soon as a bound is exceeded, release buffers/terminate workers and give a per-file explanation. Declared sizes, compression ratios and central-directory counts are only early rejection hints, never trusted as sole enforcement. Determine whether the candidate API can enforce limits before oversized allocations or output chunks; reject a candidate that cannot be bounded adequately.
2. Initial candidate is exactly one regular root member named `usage.json`. Reject missing or duplicate names, extra members, directories, nested/traversal or absolute paths, encrypted archives, unsupported compression/features and ambiguous/invalid encodings. Do not extract to a filesystem or evaluate archive content. Test discrepant headers/directory records, truncation, bad checksums, malformed archives and unsupported versions; reject the affected archive with clear reason and continue processing other selected files. Confirm what the selected library validates rather than assuming CRC coverage. Bare JSON, if authorized later, must meet equivalent byte, schema and complexity limits.
3. Decompression is not the entire resource boundary: cap decoded JSON size, nesting, collection lengths and supported field ranges before expensive processing; determine how parsing, aggregate batch memory, cancellation, responsiveness and a single oversized output chunk are bounded. Verify archive and JSON handling without network and without leaving files or workers behind. Never render imported strings as HTML or run them as code.
4. Synthetic spike should cover ordinary representative timelines and realistic sizes, ZIP round trips and direct import, genuinely distinct runs with identical summaries, repeat exports, same ID with conflicting content, malformed/truncated/duplicate-member archives, absent or dishonest size metadata, expansion beyond each limit, corrupted content, unsupported methods/version and batch overload. Record actual compressed/uncompressed sizes, timing, memory and device/browser assumptions; do not extrapolate test results to all devices. No real student files.

## Identity, duplicates, versions and evidence

A stable random run ID enables a **possible same-run** indication across re-exports, not proof of authorship, uniqueness or untampered gameplay. Different exports sharing an ID may be different snapshots or altered files; conflicting content must be explicitly shown for review, never silently merged or treated as misconduct. Different IDs do not prove different students. Exact-content matches without matching IDs may be coincidental, particularly with compact records. Let the teacher choose inclusion/exclusion and show submitted/eligible/unknown/duplicate counts; prevent silent double counting. A checksum can catch accidental corruption but is recomputable and does not authenticate a file.

Validate the versioned format, closed types, limits, sequence and evidence consistency; distinguish malformed, unsupported, incomplete and unverified. Do not fill missing evidence with false/zero or mix incompatible catalog definitions; identify exclusions and eligible denominators in each aggregate. The future contract must choose unknown-field and migration policy. The timeline preserves separate **we displayed / you did / did this affect you?** registers; impact remains a question. An action following a cue is not evidence the cue caused it.

Stable directions are manual submission, ZIP with versioned structured content, local direct import, summary plus meaningful bounded timeline, per-run random ID, privacy defaults, provenance/completeness caveats and submitted-run comparison. Exact event names, technique taxonomy, fields, ordering/completeness semantics, terminal vocabulary, action-time/day/session rules and mappings to current log remain pending Plan37 and Receipt integration. Elapsed time and session count are not established proxies for engagement.
