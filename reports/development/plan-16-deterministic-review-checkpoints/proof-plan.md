No other report, packet, source, validator, build, smoke, browser, or owner-profile files may be changed. Existing Plan 27 and Plan 33 work remains foreign and untouched.

## Source-to-recipe mapping

The pending checkpoint is created by calling the current `GameEngine` constructor, `start()`, `setupCompanion()` and `commitPromotionalTenPull()` in a development-only Node recipe with a fixed seed. That produces valid engine history but does **not** claim the companion setup or pull was displayed to a learner/reviewer. Its entire pre-load log is explicitly scripted prehistory. The checkpoint is then loaded through normal app restore and mounted gacha UI; only post-load visible card interaction supplies actual `reveal_shown` evidence. The starter recipe uses that same seeded envelope and continues only through actual mounted UI controls. This avoids a seed-injection hook and gives both checkpoints one reproducible engine-generated prehistory.

## Event boundaries

- **Pending reveal:** Complete engine-generated envelope; full hash-chained prefix through tenth `draw_committed`; no reveal entry; queue exactly matches commits; `state.step='d1_morning_gacha'`, `activeModal=null`, `phase='playing'`, story clock day 1 morning. After restore, normal gacha controls are rendered. One post-load pointer activation of the first-owned visible card back should append exactly one matching `reveal_shown` record and mark only its card revealed; engine RNG snapshots and draw-commit count remain identical. Repeating the same reveal against a hydrated engine must be idempotent and add no log entry.
- **Starter offer:** Complete envelope from continuation of the pending baseline through actual visible app controls. Capture after modal visibility, not merely after `displayStarterOffer()`. Require a valid race attempt/resolution pair and its proper timeline/callback evidence, `offer_shown`, currency offer cue, `state.step='d1_afternoon_starter'`, `activeModal='starter'`, and story clock day 1 afternoon. The branch contexts reload byte-identical starter fixtures separately; accept and decline are not run sequentially against shared storage.
- Neither recipe may splice histories or append display evidence from a harness shortcut. Every display evidence record must originate from mounted production UI callback execution. Pre-checkpoint history is synthetic, labeled scripted prehistory, and never represented as actual reviewer observation.

## Fingerprints and checks

For each fixture, compute SHA-256 from exact stored bytes (artifact identity) separately from semantic regeneration equality. Semantic comparison omits only the envelope's top-level volatile `savedAt`, then compares the full remaining envelope, state, every RNG stream, event entries/head, race resolutions and UI boundary context. Nested fields named `savedAt` remain compared. Rerun `create-pending` and `starter-capture` to compare semantic regeneration; if any event ID or other evidence differs, preserve the old fixture and report the mismatch without adding a normalization exception. Before any approved recipe/fingerprint change that regenerates an active fixture, move the active fixture, its manifest, and all generation-result records into a uniquely named `history/` subfolder. Verify each archived file against its pre-move SHA-256 and record the hashes in an archive index; keep prior browser-helper failure records in place and append new ones. Never overwrite, relabel, or silently normalize historical evidence. Manifest fingerprints identify the source commit, raw local hashes for every tracked `src/` file plus `index.html`, Vite configuration, package manifest/lockfile, and the harness recipe, as well as schema/rest evidence versions, seed and story clock. This conservative local closure includes direct imports such as apartment/ambient helpers, rig/motion modules, and apartment kits. A finite `SERVED_FILES` map separately checks response hashes for explicitly reviewed runtime entries; Vite config and package files are not fetched as runtime modules. The controlled launcher obtains the map from its own Vite process. This finite map is not full-network or transitive-byte attestation. Transformed response bytes are not claimed to equal working-tree files. A mismatch is stale and fails closed.

Validate with current `validateSave()` before writing and after each captured continuation. Hydrate both fixtures and each branch through `GameEngine.fromEnvelope()` and compare a second serialization semantically. Deliberate in-memory negative controls verify malformed schema, malformed RNG snapshot, tampered event chain, incoherent state/log and stale source fingerprint rejection; none is written to storage. Preservation demonstration uses an isolated ordinary-save context with a sentinel save: fixture load occurs in a second fresh context/profile; confirm sentinel bytes remain unchanged and no clear/remove call targets the ordinary context.

The browser witness must report actual loopback page origin/base URL, local source revision/fingerprint, exact separately hashed served module responses, fresh Chrome profile/context identity, checkpoint ID and exact fixture hash, normal loaded route/modal, observed controls, actions taken, resulting log head/schema and any uncertainty. Each phase uses a new temporary Chrome profile and newly isolated BrowserContexts. Screenshots are visual witness only; semantic save validation remains the engine/storage checks above.

## Controlled server and browser plan — proposed, not yet authorized to run

The existing Plan 25 `browser-lifecycle.mjs` and Plan 19 browser helper show useful local patterns: bind to `127.0.0.1`, select/check ports, use Vite `--strictPort`, wait for readiness, isolate Chrome in a temporary profile, and clean up owned child processes. Both serve `vite preview` from `dist/`, so they are not suitable as-is because this proof needs current source modules and no new build. The separate controlled helper has already recorded three bounded pending-restore attempts; see its append-only results. The first two failed before usable browser interaction; the owner-cleared standard-environment attempt started Chrome and failed the Skip pointer hit guard, with confirmed owned-process cleanup. No hit guard was weakened. The corrected pending-restore recipe waits for natural acquisition completion instead of retrying that Skip interaction.

If root clears a browser phase, use `run-controlled-vite-phase.mjs` for exactly one phase per invocation. It checks the exact repository root and clean tracked-source closure, confirms loopback port 5181 can be bound before spawning, then starts the existing `node_modules/vite/bin/vite.js` directly from that root with `--host 127.0.0.1 --port 5181 --strictPort --base /Quackpot/` and `VITE_BASE=/Quackpot/`. If the port is claimed after the probe, `--strictPort` must make Vite fail closed. Require bounded socket and HTTP readiness at the exact `/Quackpot/` base path before hashing entries or starting Chrome. Do not install packages or build `dist/`.

The helper registers each owned child, including PID, launch time, executable, arguments, and working directory, before awaiting readiness. It passes an explicit 1 GiB heap cap to Vite and the phase subprocess. It starts only after the committed local source fingerprint is checked and checks tracked-source identity again after the phase. Its 71-second work deadline stops Vite and gives the proof/browser cleanup time to finish; a 79-second total watchdog initiates final cleanup while leaving the Plan 25 90-second outer process-tree guard as a final bound. In `finally`, it stops only its own proof and Vite process trees, with finite waits, forced termination of only the owned trees, and residual-process reporting. Any unconfirmed process-tree termination or known residual makes the phase exit nonzero and is recorded in `controlled-vite-phase-results.jsonl`. Do not reuse or kill an unknown listener.

The helper reads the finite `SERVED_FILES` declaration from the proof recipe and hashes those entries from its own controlled Vite process before launching the phase subprocess. It rejects entries outside the same loopback origin/base, redirects, missing bodies, and responses over 3 MiB; it caps the list at 64 entries and total response bytes at 24 MiB. It passes that exact map and base URL to one `checkpoint-proof.mjs` phase. It stores full source hashes and the finite response map in `controlled-vite-phase-results.jsonl`; stdout contains only a compact summary and the evidence-record hash. This finite map is not full-network or transitive-byte attestation, and Vite-transformed bytes are not equal to raw working-tree bytes. For an interaction hit-test failure, the harness records the selector, target/hit classes and rectangles, computed stacking/pointer/visibility styles, scroll and visual viewport state, and at most one bounded screenshot of the current page. It adds no page or interaction and never substitutes DOM activation for a failed pointer guard.

Run only individually cleared browser phases through the existing bounded runner. The helper owns one short-lived server for that single phase; the proof harness itself does not start a server or another watcher. Each phase uses a fresh isolated Chrome profile/context and the authorized one-shot fixture injection. Do not parallelize phases. After each invocation, verify the owned Vite process tree exited or report cleanup residuals. If the server, proof phase, and cleanup cannot fit the limit, stop before launch.
