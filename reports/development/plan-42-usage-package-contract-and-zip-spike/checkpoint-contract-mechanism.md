# Plan 42 checkpoint: synthetic contract and ZIP mechanism proposal

2026-10-31 · Proposed for QP Orch clearance; not implemented, accepted, or production-ready.

## Experimental contract

A genuine ZIP has exactly one regular root member `usage.json`, UTF-8 JSON. The envelope has separately versioned `format` (ZIP usage package v1), `schemaVersion` (1), and `catalogVersion` (synthetic-1); a synthetic-only marker; a random opaque per-run ID supplied by the producer; `evidence` completeness (`complete`, `incomplete`, `unknown`); a compact `summary`; and ordered `timeline`. The producer retains its supplied ID across simulated re-export; a new run receives a new ID. The spike must not claim to implement production persistence. Reject unknown version or unrecognized fields in v1; classify incomplete evidence separately, never substitute zero for unknown. Summary counts are nonnegative integers or null (unknown), with zero allowed only when evidence establishes it. Require monotonically increasing sequence numbers; permit gaps because the timeline is a projection. Categories are closed synthetic identifiers: cue displayed, action recorded, outcome committed, outcome revealed, and terminal/Receipt recorded. Reveal references an earlier committed outcome; missing reveal does not imply display. Summary/timeline consistency rules and omission/truncation metadata must distinguish bounded projection from complete source evidence. No names, arbitrary text, reflection, seed, exact timestamp, or persistent installation identifier. Synthetic data is explicitly labelled and cannot be treated as game export evidence.

Current log `cue_shown`, `offer_shown`, `retention_modal_shown`, `action`, `draw_committed`, `reveal_shown`, `terminal` and `receipt_shown` are provisional mapping candidates, not an adopted adapter. Receipt uses committed odds from the actual draw record; final mappings, technique catalog, coverage, and Plan 37 life events require later design. A run ID is pseudonymous and linkable, not an identity or authenticity proof. Same ID with different content is a conflict or snapshot, not misconduct; distinct IDs do not prove distinct people. Exposures and later actions do not establish attention or causation. Manual download/submission and local-only import remain the production direction.

## Proposed initial limits (experimental, not capacity guarantees)

- One archive at a time; 20 selected files maximum; 8 MiB compressed per archive, 32 MiB total selected compressed bytes.
- Exactly one entry; 2 MiB actual expanded JSON per archive, 16 MiB cumulative actual expanded bytes per batch; reject early on larger claimed sizes but still count actual bytes. Count before copying into retention; a single over-limit chunk is rejected, with its maximum allocation and library internals investigated explicitly.
- 2,000 timeline events; JSON depth 12; each decoded string at most 512 UTF-16 code units; bounded arrays/objects and finite integer ranges. Before `JSON.parse`, enforce UTF-8 validity and use a bounded lexical depth/string scan; the 2 MiB input cap bounds the parse input, but heap overhead is measured rather than represented as a hard heap cap. Reject duplicate JSON keys if supported by a suitable bounded approach; otherwise report feasibility and stop rather than silently treating conflicting keys as valid.
- Per-file worker deadline 10 seconds; explicit cancellation; terminate and release on timeout. Batch retains only bounded validated projections, with an additional 16 MiB serialized-projection budget; no more than one worker active. Keep retained fixtures/evidence under 32 MiB. Node jobs, when authorized, use unchanged Plan25 launcher, serially, 1 GiB heap, 2 GiB sampled owned-tree memory and 90 s ceiling; coordinate Node/browser with QP Orch and Plan29.
