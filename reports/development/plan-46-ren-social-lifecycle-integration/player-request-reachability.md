# Plan 46 player-initiated request access — proposed bounded repair

Finding: at a connected player's desk in an eligible Evening, opening the temporary Ren channel auto-creates Ren's offer before the channel renders. The player-initiated “Suggest game night” and “Ask Ren to come by” controls only render without a pending offer and with no offer that day. After declining the automatic offer, `lastOfferedDay` still equals today, so those controls are not available. An odd-day Ren-generated game invitation can still be accepted; that does not make the player's request reachable. This predates the Door amendment.

Proposed revision2-only transition, not yet cleared: leave automatic Ren initiative and normal invitation display intact. Once a Ren-initiated, uncommitted invitation has actually been displayed, show an explicit alternative beside its response controls: “Suggest game night instead” when the offer is for a door chat, or “Suggest a chat instead” when it is for a game. A `social46_suggest_activity` intent names the same pending id and the other valid activity; it requires shown, Ren initiated, uncommitted, no prior conversion, ordinary availability, and the relevant scene eligibility. It records the player's action, sets a per-pending one-time conversion flag, marks the original displayed invitation replied and resets its unanswered streak, changes the existing opportunity's activity/initiator, and resets its display gate. A separately displayed finite Ren response such as “a game could work {relative evening}. want to make that the plan?” or its chat counterpart uses a new `suggestion_response` display kind. The user still explicitly accepts, declines or proposes another evening; no commitment is created merely by suggesting. If the follow-up is never shown or acted on, the answered original is not an unanswered invitation. The same id/day remains; no second invitation or repeated alternating suggestions are possible that day. Existing visit-gap and timing checks remain in force.

Unseen, expired, replied/committed, stale, already-converted or unsupported-activity requests fail without mutation. A pending plan is never displaced. Existing social revision1 and old revision2 replay is untouched because the new state and evidence are created only by the new explicit intent; no old lifecycle event changes interpretation. In strained state where no Ren-initiated offer is available, the existing player repair request continues. The new action/response have bounded Receipt fields and factual player-facing wording.

Before source writes, root reviews this exact state and event ordering. Validation must include a real connected-evening UI path from no pending offer to displayed chat invitation, Suggest game night instead, separately displayed response and explicit acceptance; the reverse path; repeated/stale/committed/unshown rejection; no new day/anchor/HP/RNG change and at most one conversion; exit/reload replay and shown-only expiry; unchanged revision1/unconverted revision2 histories. Then root views the actual updated interface before owner review. This is a targeted reachability repair, not an availability or relationship rebalance.
