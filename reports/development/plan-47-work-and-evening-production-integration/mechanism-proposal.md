## Root gate amendments: exact historical shape and guarded boundaries

**Historical JSON shape.** Policy-1 `initialLife()` must return the exact existing property set, property order and values: no new `activity: null` or other field in the initial state or any old-intent result. Frozen policy-1 initialization and old transitions reproduce historical `life_transition` snapshots byte-for-byte under the existing JSON comparison. Activity fields may first appear only in the result of a specifically new intent, or in a separately validated sidecar; they never appear retroactively in old snapshots. The replay tests compare serialized old transition payloads, final state and original hash chains against captured pre-change envelopes, not only equivalent balances.

**Activity boundaries.** For a new activity, `begin` atomically reserves an ID/anchor and persists a pending presentation before anything is shown. While pending, engine guards reject `advance`, `late_night`, `extend_session`, new work/session/leisure/activity commitments and other competing phase/anchor-consuming paths; enforce applicable rent/recovery constraints without trapping an existing obligation. Presentation progression is explicitly guarded. `complete` requires the matching pending ID and valid final presentation stage, applies the actual capped HP delta once, and transitions the durable record to `completed_awaiting_dismissal`. Acknowledgment display and dismissal are separate from the recovery transaction; reload restores acknowledgment without re-credit, and its single dismissal removes the resolved invitation. Uninstall before completion appends one factual activity-interrupted event before terminal, following the existing interruption-before-terminal ordering; validation requires it for an unfinished activity and rejects it for an already completed one. A completed activity awaiting dismissal remains completed at terminal, not interrupted. Settings must neither complete nor dismiss it.

**Selected-work boundaries.** A selected work record is bound to its exact work ID, catalog/algorithm version and selection event. Engine methods and validation enforce `selected/commute` → `work` → `completed/payslip` → `dismissed/return`, with display evidence distinct from stage transitions. Departure/agreement and selection enter one save snapshot before presentation; progressing from commute requires its valid active stage, and work completion requires the matching selected ID at the work stage. Completion atomically records the existing income transaction exactly once and the completed/payslip stage; acknowledgment dismissal and phase advance are separate guarded boundaries. Reload of each successfully saved snapshot resumes that stage without reselection, duplicate exposure or payout. No unpersisted visual state is treated as proof of display. A pre-existing pending work ID lacking a selection record is explicitly classified as legacy and retains the old `complete_work` guard and semantics. A newly selected ID cannot evade stage checks by deleting/corrupting its sidecar: validate selection and state against append-only history and fail closed. A saved post-income state must not fall back to legacy completion. Settings and Uninstall at each boundary preserve the existing receipt/interruption ordering.
