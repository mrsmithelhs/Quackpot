# Plan 47 follow-on mechanism proposal: phone, session and in-app navigation

2026-11-01 · Proposal to QP Orch; no gacha/session/DEX semantic source edits yet. The owner's rent-paper correction is separately authorized and is in progress. Keys art is separately held for a Sonnet handoff.

## Existing behavior and concrete failure

After Call Mom, `life.anchor` is the activity ID, `phase` is evening, and `session` is null. `openLifeApp()` permits free browsing; the welcome button calls `commitPromotionalTenPull()`, which calls `phone_commit`, rejected as `anchor_used`. Existing `extend_session` requires a non-null session, so it cannot address this empty-session case. A same-phase session has one pull and one race; either kind can still be used once without extension. Existing explicit `extend_session` mutates phase before another actual play; moving that action out of the hub and making it contingent on the next real play changes that boundary. A Late Night pull/race, not browsing, sets next-morning fatigue; morning arrival, recovery and due-rent priority remain existing authorities.

## Proposed intent and transaction boundary

Add only `phone_commit_next`, version 1, with `kind: pull|race` and explicit `confirmed: true`, to the existing pure life transition. It is valid when (a) the existing session already used the requested kind or (b) evening has a used non-session anchor and no session. Case (b) is offered only for Evening → Late Night. Validate the same current obligations/meal/recovery/work conditions as the existing advance/extend route, and reject unknown version, stale session/phase, or an unused current allowance. Compute the next phase and its obligation/fatigue effects on a cloned candidate, then verify it can accept the requested new session/anchor before returning success; if arrival causes due rent, unsurfaced shortfall, collapse/recovery, or a newly required morning meal, reject the composed action without advancing or charging. Arrival, anchor/session creation, `life_session_commit`, and Late Night fatigue flag are one `life_intent` / effects / `life_transition` batch. No parallel clock or independent session store. Existing `phone_commit`, `extend_session`, and old replay bytes remain unchanged for historical histories. Nonempty session: the other unused kind stays in the same session; reusing a used kind triggers a warning and only the successful subsequent play enters the next phase. In afternoon, warning names the missed scheduled shift; Evening → Late Night warning states the existing next-morning fatigue consequence. Going past Late Night must not bypass morning recovery/rent/meal obligations.

The controller determines the target intent at the point of actual confirmed pull or Start Race, not hub entry, Dex/browse, race-form selection, or opening Settings. Before Evening used-anchor phone entry, show a brief non-committing advisory that opening/inspection is free and active play will ask before Late Night. Cancel leaves the phase, RNG, wallet, anchor, log and welcome entitlement unchanged. Confirming an unaffordable/invalid pull or invalid race choice also changes none of those; validate affordability, pending reveal, roster/trial and phase candidate before mutation. No duplicate welcome grant.

For the **new composed path only**, create an isolated draft of the engine-owned state and append-only log plus root/draw/race/event PRNG snapshots; do not hydrate from storage or mutate a live engine during preparation. A focused helper can instantiate a draft engine and `structuredClone` the current state, `EventLog.hydrate` the current already-in-memory chain, and restore the four stream snapshots. This bounded chain copy occurs only when the player confirms a next-phase play, not every render or ordinary same-session action. The draft invokes the existing promo/paid pull or race commit with a private explicit composed-reservation parameter; no second `phone_commit` is made. Validate amount, pending reveal, roster/trial, and candidate transition before allocating outcomes. The draft resolves and serializes the real outcome, appends the composed life batch and the existing purchase/draw or race choice/resolution, then only on full success publishes the draft's state, log and streams to the live engine as a single synchronous action before autosave/render. Reject/throw discards the draft: live log head, phase, balances, roster, reward state, rest activation and all streams remain untouched. This is a bounded proposed seam for this one operation, not a general transaction framework. Any existing displayed race-choice/rest evidence emitted *before* the player starts remains truthful pre-existing history; a failed start adds nothing further.

For race, `runRace` currently calls `activateRaceRestPolicy()` before resolver/serialization and its existing normal-path throw-after-write risk predates this repair. The draft contains that activation, so a resolver/serialization failure on the **new** composed path discards it; success preserves activation before life reservation and `race_choice`, and existing ordinary-success ordering is unchanged. Existing normal-action failure behavior is not silently broadened. Preserve injected resolver/serializer failure test hooks on the draft. For pulls, staged draft calculation prevents a thrown draw/log operation from publishing the reservation or consuming the live RNG. The existing same-session action path and all historical success ordering stay unchanged. No durable crash guarantee is claimed if autosave is disabled or fails.

`validateLifeHistory` recognizes version 1 new composed intent, replays it with the same pure transition, and extends the existing `phone_commit` correspondence check to require immediately following actual purchase+draw / draw or race_choice as appropriate. It rejects an isolated phase/session transition lacking its actual outcome, a mismatched kind or duplicate commitment. Existing marker-free schema-4 envelopes and all old life intent meanings remain valid, without rewriting chain bytes or reclassifying old explicit extensions. Unknown composed versions fail validation. Tests should independently assert exact log chronology, state, RNG and currency on declined, unaffordable, invalid-roster, resolver-failure, restored and terminal paths; not simply compare engine and validator through one helper.

## UI source seams

Move Duck-Dex access from global HUD to a small shared in-app navigation component on the real life hub, reveal/card, race form and result surfaces (and appropriate legacy views if still reachable); preserve `dexReturnStep`, save/restore, focus and factual `recordDexViewed` evidence without adding a second view or a duplicate button per surface. Global Save/Settings/Return/Uninstall stay outside fiction. Remove `Finish session & advance` and explicit `extend` from the fictional hub. Apartment uses existing phase-appropriate advance/late-night controls, with consequence wording such as Turn in for the night where that meaning is accurate. Returning from phone to apartment only suspends a real session; reopening in the same phase resumes it. Empty phone browsing never constructs a session or advances time. A future play request after using its allowance or after a used Evening anchor receives the explicit warning then uses the composed transaction above.
