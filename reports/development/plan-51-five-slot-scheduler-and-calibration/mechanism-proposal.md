## Proposed authority and lifecycle

- Serializable state holds policy/config identity, day and slot, monotonic revision, current reservation and durable activity cursor, per-day meal/shift outcomes, future plan references, session action allowances, pending fatigue/recovery and obligation status. Economic balances and gameplay RNG remain engine-owned; the pure interface receives a snapshot and returns changes/events for one atomic engine transaction. It must not duplicate the gacha engine or manufacture outcomes.
- `inspect(state, balances, intent, context)` returns eligibility, exact current/destination slot, costs, clamped HP changes, displaced obligations, social conflict alternatives, required disclosure and a revision-bound proposal. Inspection never changes state or RNG. `commit(...)` revalidates revision and facts and returns new state, balance deltas and factual events, or a failure without gameplay change. Engine must atomically couple this result with the actual successful pull/race/purchase and RNG mutation; the scheduler alone cannot prove that integration. Displayed warnings/cancel are separately recorded only when actually shown/chosen. Unique activity/operation IDs and completed IDs reject stale or duplicate operations.
- `start` reserves one current slot; `resume` preserves cursor; `complete` once applies completion-only pay/reward and advances. Meal buy/skip completes promptly. Work and Ren suspend/resume with no premature pay/reward; explicit abandonment closes the occupied slot without completion reward, preserving earlier outcomes and separately recording social facts. Exact abandonment/recovery interaction remains gated. A gacha session begins only with a successful pull or race; each allowed action commits independently, at most one pull action and one race. Browsing/suspension is free; explicit finish advances; an additional action after an allowance is exhausted first ends the prior session and requires a separate eligible slot and confirmation. Failed second operation cannot erase first operation or consume the next slot.
- Closing a meal slot through a successful competing start records one missed meal and actual capped HP loss, no charge. Completing scheduled work pays once; a competing Midday start records the missed scheduled shift once. Work availability is input data. Late Evening active start records fatigue once for the chosen policy; arrival/normal sleep does not. Early bed consumes Evening and skips Late Evening active opportunity; its recovery is a candidate, not selected. No wall-clock transitions.
- Separate guidance function uses Day1 guided, Days2–6 supported, Day7+ familiar fade; costs/terms and new/escalated consequences remain visible. Proposed evidence shapes: `warning_shown` with actual warning ID/context, `choice_cancelled` with proposal ID, `activity_started/completed/abandoned` with activity and slot IDs, `obligation_missed` with actual effect, and separate operation outcomes from engine. Names are interface proposals; Plan52 must map to actual append-only Receipt evidence and validate replay.
- Supported meal-related withdrawal proposal: before an unstarted Ren visit, allow an explicit return to the pending meal without claiming the visit or creating a new invitation; preserve the same plan and arrival cursor. If a player explicitly communicates inability, close that existing plan as notice, not broken; recovery exemption stays distinct. A competing committed Evening action still requires actual conflict choice. Further opportunity/relationship consequences need owner selection, not invented counters.

## API gate amendment — proposed signatures and minimum persisted state

All functions are synchronous, deterministic and side-effect free; inputs/outputs are JSON-compatible, with no clock or RNG access. `createSchedule(policy, calendar)` validates the versioned, complete policy/config and explicit work-availability data, and returns the initial schedule. `inspect(state, balances, intent, context)` returns either `{ok:false, reason}` or `{ok:true, proposal:{revision, operationId, intent, slot, destination, costs, hpDelta, displaced, conflicts, disclosures}}`; it does not reserve an ID, mutate state or assert that a warning was displayed. The caller supplies a stable unique operation ID and separately records actual disclosure/cancellation. `commit(state, balances, proposal, operation)` re-inspects against current state and requires matching revision, operation ID and canonical intent, an affirmative required conflict/disclosure choice, and a validated success receipt appropriate to the operation; it returns `{ok:true, state, balanceDeltas, events}` or `{ok:false, reason}` without changing inputs. `guidance(day, consequence, history, policy)` yields disclosure requirements independently of gameplay outcomes. Exact receipt validation for a pull/race is an integration contract: the owning engine validates and applies its real operation and scheduler result in a single transaction, never trusting a UI-provided success flag.

Minimum persisted state: `{schema, policyId, config, day, slot, revision, nextActivityId, active, completedOperationIds, obligations, futurePlans, fatigue, recovery, workCalendar}`. `active` is null or `{id, kind, day, slot, status, cursor, pullUsed, raceUsed}` as applicable; `completedOperationIds` is an append-only mapping of operation ID to intent fingerprint/result reference, with reuse rejected even after slot advance. `obligations` contains per-day breakfast/dinner/shift status and rent identity/status; `futurePlans` holds stable plan IDs and intended day/slot without claiming current time. Fatigue and recovery each carry explicit pending/resolved IDs; state and factual intent/outcome events are sufficient for new-policy replay. Final implementation can refine representation without removing these guarantees. Storage size limits and history compaction are Plan52 integration concerns and cannot weaken duplicate protection or replay.

For a first or further pull/race, the engine stages its own eligibility, cost, RNG and resulting outcome together with the scheduler transition, then commits both only on success. A session extension stages prior-session completion, next slot and new action as one candidate transaction: a failed next operation leaves the old active session, slot, allowance, balances and RNG unchanged; already successful actions remain committed. Retrying a committed operation ID returns a duplicate rejection and performs no side effect; a genuinely new action uses a fresh ID. `complete`/`abandon` are also id-bound operations; neither can duplicate pay, recovery, reward or slot advancement. Actual warning and cancellation evidence can append independently from these gameplay transactions.

Orchestration clarification: Day1 Skip applies to that meal only; the tutorial and required first shift remain. Supported meal withdrawal refers to returning to the actual pending meal before claiming a visit, with the existing reservation and opportunity intact, and does not assume dinner and an Evening visit share a slot.
