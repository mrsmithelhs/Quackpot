# Action-triggered unpaid-obligation confirmation — proposal only

The owner requested a second-stage in-game Decide panel with a clear game-ending consequence and a reconsider choice. Earlier owner direction removes the standalone “Leave Remaining rent unpaid” action and puts its warning on an action that would leave rent unpaid. This proposal preserves both selections. The related financial-ending narrative scene before the Receipt remains a separately gated proposal in `owner-ending-scene-proposal.md`; it is not silently included here.

## Current behavior and limitation

`openFivePayment` in `src/ui/life/life-view.js` renders `Leave ${bill.label} unpaid`, and `onFiveSlotLeaveUnpaid` in `src/main.js` uses `globalThis.confirm`, including the unfamiliar “Running on Empty” title. Only after acceptance does it prepare/commit `leave_unpaid`. A native confirm is an implementation choice; no inspected platform limitation requires it. `life-coordinator.mjs` rejects many schedule actions with `financial_obligation_due` unless recovery or the specific reserved-rent-shift rescue path applies. Some intended actions, such as work keys, are currently hidden while due (`keysAvailable`); simply changing a confirmation widget cannot realize the earlier action-triggered selection. `life-finance.mjs` owns the default reason and terminal effect, and `game-engine.mjs` requires actual `life52_due_options_shown` evidence before default; `life-replay.mjs` validates that evidence and event order.

## Proposed experience

The player first chooses an actual, otherwise meaningful action that would advance beyond a due payment. If the action is permitted by current rescue/recovery rules, perform its existing flow normally. Only when the actual attempted action conflicts with the due obligation should a second-stage Decide appear, identifying the action and outstanding bill(s). Candidate wording for rent: “Rent is still unpaid. Continuing without paying will end the game.” Offer “Reconsider” and “Continue without paying”; for a later-rent housing-loss outcome also say the player will lose the apartment only when the actual selected default reason supports that fact. A due-loan variant names the loan and the end-of-run consequence. Never use an unfamiliar ending title as the warning. The owner approved this direction with “end the game” wording.

Reconsider, Escape, backdrop dismissal, Settings, Uninstall/Stay or reload before confirmation do not pay, spend, advance a slot, perform the chosen action, or end the run. Reconsider returns to the same unresolved payment/action context and preserves valid rescue choices. Uninstall remains immediately accessible under its existing flow, not a hidden default trigger. Free room navigation and reading must never trigger a default. No separate explicit leave-unpaid action remains in the final interaction.

Because existing default is terminal, confirming ends the run; the requested activity is not executed afterward. Retain the chosen action's identity in the transient pending decision for intelligible copy and safe revalidation. Do not invent a new persistent event or claim it was recorded unless a separately approved log/replay contract is added. If multiple obligations are due, apply the currently selected due ordering and do not select a different bill based on button order; a concrete default target/order needs an explicit technical disposition. Recovery first remains mandatory, and a valid reserved shift, sale, deliberate payment or offered loan must not be incorrectly treated as abandonment. A 0-HP/recovery collision and approaching or simultaneous loan deadline must preserve the selected priority and distinct terminal reason.

The existing coordinator recognizes a valid rent rescue only when there is no due loan and a reserved shift matches a due rent, through its reserved Evening. Within that window it permits meal, sleep, starting work or quiet, matching overtime, and progress/complete/abandon of active work, quiet or overtime. This is an exception to preserve, not a new general authorization for those actions. The social adapter has a separate due block and must not be assumed to share that exception.

**Multiple obligations:** `dueObligations` currently returns pending latched rents followed by loans as an implementation array; `prepareFinance` accepts an explicitly named due rent or loan and defines no canonical priority. Neither is evidence of a selected default priority. The owner's loan-before-work decision does not itself determine which ending wins when multiple obligations are already due. Root must specify the target rule or preserve an explicit bill-specific decision without inventing an ordering; source clearance cannot rely on array order.
