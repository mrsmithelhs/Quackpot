# Bounded launcher: process identity diagnostic options

Status: read-only proposal; Chromium and additional runtime tests remain paused. The prior job's receipt established `InvalidOperationException` during `monitor/capture-verified-descendant`, but omitted a safe subtype. No raw exception message or host process identity is needed to report the subtype.

The current sampler explicitly throws that type for five distinct conditions: creation time equal to or earlier than the verified parent's, creation time after the first snapshot started, missing or changed parent edge in the confirmation snapshot, root or intermediate parent exit/identity change during confirmation, and descendant exit/identity change or a previously captured PID with a different creation time. The same type can also arise from .NET `Process.StartTime`, `HasExited`, `Refresh` or other handle access if a process exits during inspection. `ArgumentException` from opening a PID is currently treated as vanished; without an already-open verified handle, a missing process or reused PID must not be silently treated as a verified descendant.

Smallest diagnostic change: replace each intentional rejection with a private custom exception carrying a fixed, allowlisted reason code such as `creation_order`, `post_snapshot_creation`, `parent_edge_changed`, `root_identity_changed`, `parent_identity_changed`, `child_identity_changed`, or `captured_pid_reused`. Mark the current sub-operation before each .NET call; record only operation, exception class and optional native error code. Never emit raw exception messages, command lines, paths or PIDs into public evidence. If an identity-verified, already-open child or parent handle independently reports `HasExited` (or `WaitForExit(0)` succeeds) and its previously captured creation identity matches, classify it as an observed exit race and exclude it from future sampling; verify that no child descendants depend on an unverified parent edge. If an identity was never established, `HasExited` is inaccessible, the handle cannot prove exit, creation/parentage is ambiguous, or a PID may have been reused, fail closed and never terminate the ambiguous process. A parent dying while a child remains live is not automatically a safe child exit: preserve uncertainty and stop. Correctness tests should exercise each safe reason, verified exit race and inconclusive case without weakening memory/time limits or treating an inaccessible live process as gone.

Alternative considered: an existing reviewed Windows Job Object supervisor that creates the owned root suspended, assigns containment before allowing execution, then can account for and stop the actual job. A repository search across `scripts/` and development report `.ps1`, `.mjs`, and `.cs` files for `CreateJobObject`, `AssignProcessToJobObject`, `JOB_OBJECT_LIMIT`, `CREATE_SUSPENDED`, and `job object` found no such implementation. This is not proof none exists elsewhere or that an external binary is suitable. No dependency installation, new supervisor implementation or execution is proposed here. The minimal allowlisted-reason/verified-exit investigation is the smaller next step if root accepts it; otherwise retain the existing fail-closed stop.

## Cleared refinement and controlled results

Orchestration cleared the allowlisted reason codes and verified-leaf-exit refinement. The launcher now records stable codes for its explicit ancestry/creation/identity rejections. It accepts a vanished process as an exit race only if an already captured process handle positively reports exit and the inspected snapshot contains no dependent child edge; inaccessible or unrecorded identities still fail closed. No recursive or unrelated-process termination was added.

In a fresh-host controlled test, an intentionally ambiguous creation-order condition produced a nonzero structured receipt with `FailureReasonCode: creation_order`. A separately injected access-denied condition produced `Win32Exception`/native code 5 and nonzero status. A harmless parent/short-lived-child test recorded `VerifiedLeafExits: 1`, but the whole test then failed closed with `uncaptured_or_inconclusive_exit` during the same monitor operation; its root and two captured descendants exited and the output drain completed. Thus the exit-observation branch was exercised, but the test did not prove the launcher can finish that process pattern successfully. The underlying first Chromium failure's subtype remains unknown. No browser or production test was rerun, no catalog entry was promoted, and root disposition is required before any further launch.
