# Header messages and Quackpot phone: integration investigation (proposal only)

## Selected intent and current behavior

During the Day 3 review the owner selected: the available desk phone opens Quackpot directly; work and Ren communications and the payday-loan statement belong in a global header messages area; a small icon pulses for messages waiting to be read. The owner also selected a loan statement with a Decide panel and separate unread versus due status: opening a message clears its unread signal while it remains available to reread, and an unpaid loan remains marked due separately. These selections are intent; the architectural options below are not implemented behavior.

`lifePhoneKind` (`src/ui/life/life-phone-context.mjs`) currently chooses Work when a scheduled Midday shift is available. `objectsFor` in `src/ui/life/life-view.js` renders that message as the phone primary; when Ren is introduced it adds a phone choice menu, and when an unpaid loan exists the loan statement becomes the primary. This is why the Day 3 desk screenshot showed Work. The separate work-key action calls the existing scheduled work story, so the phone's work display is not needed to start that shift. In the current work-primary state the desk phone itself does not offer the normal Quackpot route. The header (`src/ui/hud.js`, `main.js` `updateHud`) has Save, Settings, conditional temporary End run, return and Uninstall, but no message list or unread model.

Plan28 investigated a phone/work-message communication grammar; Plan38 established actual invitation/reply/ack evidence; Plan47 recorded direct Quackpot access alongside separately reachable family actions; Plan46 owns Ren offer/response/display lifecycle. Those artifacts are provenance rather than a specification of a global message inbox. Plan49's study-level assumptions predate the accepted five-slot schedule. The current development index does not establish a dedicated implemented global message center.

## Boundaries and smallest coherent slice

A standalone phone-content correction must not remove the only reachable work, Ren or loan route. It could offer Quackpot as an additional choice temporarily, but that would not yet satisfy the owner-selected Quackpot-only phone. Recommend one separate follow-on packet that mounts the replacement header routes and changes the phone together in one coordinated source/save transition. Limit initial senders to existing work information, existing Ren messages, the existing payday-loan statement, and the existing Quackpot launch invitation/ack where its lifecycle requires access. Do not invent new company/coworker content, a general-purpose framework, or a music/social network. The work keys remain the work departure action. Any first-day invitation is retained with its actual reply/ack evidence and may not become an automatic install or reward.

The header icon is navigation to a local message list; viewing a list consumes no game slot, no currency, and no RNG. Show a text/accessible unread count or status in addition to the pulse; respect reduced-motion with a static unread indication. Opening and closing the list restores the previous game/scene/phone/Settings/retention context without accidentally finishing a session, re-awarding a result, or displacing forced recovery. Decide whether access while a race animation or committed reveal is underway is deferred to a safe boundary; neither discard the pending outcome nor force a watch/wait. Uninstall remains immediately accessible. No runtime network or telemetry is introduced.

## Unread, due, and action identity

Unread describes whether a particular delivered message revision has actually mounted and displayed its content; clicking the inbox icon or beginning a failed load does not clear it; it is distinct from an unpaid balance, due deadline, unanswered invitation or other actionable obligation. A read loan statement retains an explicit outstanding/due signal; this distinction is owner-selected. Keep read messages reviewable while relevant; do not infer an unread ledger from `social46.pending.shown`, `response.shown` or another field whose current purpose is recording actual display and lifecycle. The existing Ren state has actual shown, reply, reschedule, conflict and response records, some appended on view. Reopening, closing, Settings or reload must not create another offer or duplicate shown evidence. No notification pulse should start merely because a hypothetical or not-yet-delivered event could exist.

A bounded design must enumerate identity, delivery and expiration for each source, including changed loan amount/deadline, Ren offer revision/response, work notice per shift, and reply acknowledgment. A new revision may be unread even if a previous one was read; canceled/expired items must not pulse indefinitely or claim to be available. Actual display is logged only when shown; an inbox indicator is not proof the message was read. Authoritative due/recovery state continues to govern whether a payment or social action can be selected.

Asked whether the payday-loan message should open its statement and offer the existing Repay choice, including when due, the owner answered: “Show the statement plus a Decide panel.” The proposed panel retains the existing deliberate repayment choice. This must preserve due-before-work at Midday, unpaid obligation handling and recovery-first on zero HP. A message cannot mark a payment made by being opened. Do not remove the existing payment path before the replacement is reachable; if simultaneous rent/loan are due, the payment presentation must retain both obligations and their selected priority.

## Save, replay, lifecycle and testing proposal

Current format is schema 5 with canonical scheduler/finance and append-only event log; `main.js` autosave/restore and `storage.mjs` validate it. A durable message-read model would require an explicitly reviewed representation and replay/validation contract, not an unlogged UI-only flag or a new interpretation of legacy social fields. Root should choose whether read/delivery facts are idempotent append-only events with stable message IDs or another deterministic, validated representation; map one commit per delivery/read and avoid duplicate transitions on reload or overlay closure. Propose preserving current development save bytes with an explicit supported transition or explicit unsupported handling under owner policy; no migration is promised until designed. Owner review profile is never mutated by synthetic tests.

Acceptance scenarios: Day 1 invitation/reply versus ignore and later free pull; Day 3 scheduled work with Quackpot accessible and work departure through keys; Ren first contact, offer/response, unread versus unresolved, re-open/reload and conflict/couch disclosure; pending and due loan, early repayment, simultaneous due bills, 0 HP recovery and work cutoff; new message revision, canceled/expired message, exact once delivery/read; save, reload, Settings and Uninstall/Stay; active phone session, unrevealed committed cards and race result; keyboard, screen reader labels, reduced motion and narrow/wide HUD. Prove ordinary reading/navigation preserves time, finances, health, inventory and RNG except specifically recorded shown/read evidence; use negative controls for duplicate identity and unauthorized state mutation. Browser evidence should distinguish genuine replayable parents from test-only synthetic states.

Before production: root allocates/clears the follow-on packet, exact source ownership, read-state/transaction/save/checkpoint proposal and recipient/notification boundaries; resolve any remaining load-bearing experience decisions around delivery, expiration and interaction placement. Existing Plan52 13 checkpoint entries are source-stale from the current feedback batch and require a final refresh after source stabilizes; a separate message-model change would require its own current-source checkpoint disposition. No production source writes, packet completion or deployment are authorized by this report.
