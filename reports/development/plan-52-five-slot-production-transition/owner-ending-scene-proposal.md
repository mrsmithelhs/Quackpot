# Plan 52 owner-review ending scene — read-only proposal

Status: owner requested placeholder narrative scenes and clear warnings; not approved for production integration. The affordable-rent presentation repair is separate. Existing evidence and current state, not a final creative ending design.

## Existing outcomes and observable distinctions

Five-slot financial defaults record a terminal event with a reason, obligation ID, amount and `housingLost`. First-rent `withheld`/`unaffordable` and loan `refused`/`unaffordable` lead to `running_on_empty` without `housingLost`; later-rent `withheld`/`unaffordable` records housing loss. Do not describe eviction for a first-rent or loan default unless an actual event establishes it. The legacy escalation exhaustion path also uses `running_on_empty` but lacks the detailed five-slot evidence and needs neutral fallback copy. Voluntary `run_complete` and `uninstall` are distinct existing terminal routes; there is no independent HP-death ending in the five-slot path (0 HP causes recovery). Do not invent outcomes or change routes.

## Proposed presentation and lifecycle

For each actual financial ending, show a concise, cause-specific placeholder narrative after the terminal transaction, then a clear Continue to Receipt button. Use the event reason and `housingLost` evidence to distinguish actual cases. Warnings should name the consequence in plain words (for example, that the run will end; describe apartment loss only for a housing-loss path), not rely on an unexplained ending name. Preserve an understandable non-accusatory distinction between inability to pay and deliberate withholding/refusal. Avoid inserting a blocking scene before immediate Uninstall; its accepted exit/retention flow stays intact. Whether ordinary run completion needs a distinct scene or already has sufficient final presentation is an owner-experience scope question, not an inferred new ending.

Projection of an unpresented ending could use the existing terminal event and `phase=terminal`; after Continue, actual Receipt rendering appends `receipt_shown` once and phase becomes `receipt_presented`. No new schema field is necessarily required if the UI derives the pending scene only for supported financial terminal evidence. This requires verifying current state normalization, schema-5 save/load and existing receipt-shown evidence; previously presented Receipts must remain Receipts rather than fabricate a past scene. If additional scene display/action events are desired, that expands the log/replay contract: `life-replay.mjs` currently accepts only `receipt_shown` after a terminal event and needs explicit versioned handling and old-evidence support. Do not record a scene that was not shown, or `receipt_shown` before the Receipt is actually mounted.
