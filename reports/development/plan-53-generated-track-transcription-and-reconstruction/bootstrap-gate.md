## Supervision and host evidence

`bootstrap_supervisor.py` uses suspended launch into a kill-on-close job with an aggregate 4 GiB job commit limit, 30-minute wall ceiling and one-second sampled workspace/log and free-disk checks. It stops on sampled workspace above 20 GiB, free disk below 30 GiB, diagnostic log above 1 MiB, monitoring failure or timeout; then terminates its owned job and checks that root exited and the job reports zero active processes. Limits on disk/log are sampled and can overshoot between samples; the job memory cap is commit accounting, not a sampled private-memory peak. Recorded sample gaps must be reviewed. Output redirection uses inheritable handles in a single-threaded supervisor; verify no unrelated inheritable handles and avoid credentials in environment or arguments. No broad process kill.

The wall timer in the polling loop can be delayed by a stalled filesystem enumeration. `bootstrap_watchdog.py` now adds an independent outer timeout, and the supervisor uses STARTUPINFOEX to assign the job atomically at process creation and explicitly allowlist its two standard handles. **Neither control is yet validated:** the first handle-list smoke test failed with child exit 1 and its temporary log was lost. Root authorized two corrective attempts. The first exposed Windows `0xc0000008` for an invalid handle; the second observed the same numeric handle value as valid in the child. Because handles are process-local and can be reused for a different object, this is ambiguous; object identity must be checked. In all attempts the supervisor reported root exit and zero active job processes. The watchdog test and resolution were held, and the resource turn released. Free host RAM is checked before launch rather than continuously. These controls are not yet clearance to run resolution.

Three synthetic tests, each with a 128 MiB job and 10-second outer guard, passed on 2026-11-02: normal exit (0.064s); one-second timeout with owned sleeping child (1.056s); injected storage-monitor exception (0.125s). Each checked root exit and zero active job processes. They do not establish arbitrary breakaway containment, full host visibility, sustained 30-minute behavior, all exceptional paths, GPU behavior or network isolation. Assignment failure and cleanup failure paths are implemented but have not been synthetically witnessed. Never treat a test as clearance.

Read-only host-wide CIM inspection on 2026-11-02 found 31.31 GiB total and 11.18 GiB free RAM at one instant, C: 309,699,104,768 bytes free, and GPU query 0/8188 MiB used. Running applications were present. These measurements are not a reservation and change continuously. Proposed bootstrap preflight requires 8 GiB free RAM, 30 GiB free disk and root confirmation that competing work is coordinated; the 4 GiB job cap leaves a nominal 4 GiB margin at that floor. Inference retains its separate 16 GiB free-RAM and 6.5 GiB free-VRAM preflight; the observed 11.18 GiB would fail that inference floor. `host-preflight.ps1` requires real host CIM access, emits only process names/IDs/parent IDs and working sets, and returns nonzero for failed checks; review its output locally before sharing. Numeric floors are not proof no heavy jobs conflict. Recheck at the actual turn; do not kill or restart unrelated processes.

A later escalated validation of `host-preflight.ps1 -Stage bootstrap` returned exit 0 and measured 9.8 GiB free RAM, 288.35 GiB free disk, 625 processes and 8188 MiB reported free GPU. It met numeric bootstrap floors only; it did not establish absence of competing work and is not an inference approval.
