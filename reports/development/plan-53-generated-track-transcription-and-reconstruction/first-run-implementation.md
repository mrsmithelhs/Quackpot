## Proposed exact operational boundary

The one benign, root-cleared launch observation found the exact venv `Scripts\python.exe` launcher as parent and extracted base `python.exe` as the executing child; `sys.executable` reported the venv path. This establishes that benign two-process launch only, not all future model/helper behavior. A one-process job limit is unsuitable. Revalidate both executables' hashes immediately before any future run, and require a job that cannot break away. Restricting the active count to two is a possible guard, but cannot independently prove every descendant's identity or stop network access through OS services; polling can miss short-lived processes. Do not present it as a complete sandbox.

A concrete Windows Firewall candidate would create uniquely named, temporary **outbound block** rules for each verified venv/base executable at their exact paths, scoped to all profiles, and remove only those rules in `finally`. Rule creation/removal changes machine-wide policy and may require administrator privileges; no such live action is authorized or executed. A trial script exists but its cleanup is not independent of its own process. Before deciding whether this is sufficient, a separately cleared no-model test must show the expected rules are active, direct-IP and hostname/DNS attempts from the actual launched tree fail, any subprocess/helper attempt cannot escape the policy, local file access still works, and the rules are removed even on failure/timeout. Windows DNS service delegation and unobserved executable paths remain unresolved; a process-count limit or sampled process list alone cannot close those gaps. If the candidate cannot enforce the whole tree and name-resolution boundary, request a stronger OS isolation approach or explicit root disposition; do not silently rely on `HF_HUB_OFFLINE`.

**Single proposed system-boundary action for root/owner disposition:** allow one short, coordinated, administrator-mediated no-model trial that (1) confirms neither unique rule name exists, (2) creates two rules with the exact resolved and hash-verified venv/base paths using `New-NetFirewallRule -Name RULE -Direction Outbound -Action Block -Program EXECUTABLE -Profile Any -Protocol Any -RemoteAddress Any`, (3) reads back each named rule and application filter and verifies the expected outbound/block/enabled/all-profile/all-protocol/all-remote scope, (4) runs the actual venv→base launch in an owned job to test direct-IP and hostname/DNS attempts, a deliberately attempted child and local-file access, and (5) removes **only those exact two newly created names** using `Remove-NetFirewallRule -Name RULE` in cleanup and confirms both are absent. A separate nonblocked control must establish test endpoints/network availability so an already-offline host does not create a false pass. Probe requests contain no source audio, model content or credentials. The owner must authorize the actual temporary system-rule modification, any admin prompt and the limited network test if root selects this option. An independently supervised cleanup plan must handle interruption, and any inability to create, inspect, test or remove rules must stop the trial. The trial script is implemented but is not an effective or verified boundary; DNS-service delegation and unknown helper behavior may still make it inadequate even if basic probes pass.

Once real containment is reviewed, a separate root-coordinated run requires >=16 GiB available physical RAM, >=6.5 GiB free GPU memory, >=30 GiB free disk, no competing heavy jobs, at most 20 GiB sampled whole workspace, a per-item 8 GiB job-commit cap and independent 15-minute watchdog. `inference_monitor.py` implements a proposed device-wide
