## CPU-first initialization check

Read-only inspection of the installed 0.4.0 implementation did **not** establish a supported public CPU-to-CUDA transition for a `TranscriptionModel`. It is a wrapper, not an `nn.Module`: its constructor stores `_model`, `_tokenizer`, and `_device`, and transcription explicitly allocates or moves inputs on `_device`. The underlying conditioning provider, mel conditioner and class conditioners also keep plain `device` attributes used to create/move tensors. Moving only `_model` tensors with `.to('cuda')` would not update those Python attributes. `_build_model` also configures a CUDA `TorchAutocast` only when constructed for CUDA; a CPU-built model retains a disabled autocast context. Fixing these details would rely on private internals or an upstream-supported API change and is not a documented equivalent transition.

The installed safetensors `load_file` declares `backend='mmap'` by default, but the mapped state, the initialized float32 model, any half-precision conversion copies, Python/PyTorch overhead and final device transfer have not been measured under Windows or against the 8 GiB job-commit ceiling. A rough single full float32 weight-sized allocation is 5.09 GiB and a full half-precision one is 2.55 GiB; even their simplistic sum leaves little space under an 8 GiB job before runtime and allocation overlap. Mapping does not establish zero process/job commit or a safe peak. Release order and device-transfer behavior remain unverified.

**Disposition:** a simple supported API-only CPU-first move has not been demonstrated. Do not build a custom loader, modify private device state, download Large or raise the limits as an implied follow-up. Root can separately decide whether to investigate an upstream-supported memory-efficient initialization or request a bounded implementation proposal. The FP16 candidate and 24 GiB single-copy disk budget above are feasibility candidates, not an executable clearance. No GPU/host memory peak for Large has been measured here.
