## Exact source and parity

`injury-replay-core.mjs` reconstructs historical input and the **entire** saved case shape from the historical susceptibility runner: seed, arm, player stance, rival choices, status/reason/guard, every ordered contact (ID/tick/participants and every recorded roll field), participant contact/roll/injury summaries, target witnesses, individual crossings/times, first/last times and adviceEligible. `requireHistoricalParity` uses strict deep equality with the corresponding saved case. `injury-replay.test.mjs` contains four pure tests: complete shape/equality; altered contact tick, roll value, crossing, advice count or guard must fail; only the four named input combinations allowed; and failure, pending, partial, duplicate or malformed publications rejected. These are proposed, unrun tests.

`injury-motion-replay.mjs` verifies SHA-256 of the retained historical pin manifest (`4856561b71a59b43946d5b455209e2e1fd3ffd13d60911b03c05a1c71b0baf10`) and its entire listed closure; verifies saved first/contact JSON bytes against `6b71561d3b6f8fbb367704363840769e52c0f1e8fb7ce7cb7d92baba75e2ef61` and `0ee9b64069e70999002505e3be9c310f4b10229df999e917ba3325f5b25efe9d`; repeats historical closure checks immediately before/after each of the four resolver calls. It compares each exact saved case projection and requires `finished` before retaining data. Only after all four pass does it write four exclusive trajectory files, then a closed `complete.pending` manifest linked exclusively to `complete.json`; the pending marker is removed only after linking. On failure, a `failure.json` reports actual calls and error. The viewer rejects a failure marker or pending marker even if a completion file exists; partial output must never be presented as a completed replay. Preexisting output directory prevents a retry/overwrite. Outputs include only real trajectory snapshots, saved-case projection and hashes, no invented histories; 8 MiB combined hard ceiling checked before writes. Files and handles are closed before publication; failed output is retained for diagnosis and not retried automatically. This is a reconstructed match, not original footage.

Historical `injury-susceptibility-pins.txt` and both saved arm JSON remain unchanged. `injury-motion-replay-pins.txt` records exact proposed replay core/tests/runner, viewer/server and read-only rig closure plus historical pin and saved output bytes. Check before each bounded job; any source drift stops. The historical producer is not edited. Prior-stage source discrepancies documented elsewhere do not apply to this current susceptibility pin list, which was checked read-only at preparation; no claim of exact replay until actual four-case equality succeeds.

## Viewer and isolated preview

`injury-motion-viewer.html/.css/.mjs` is a report-local study UI. It refuses to reveal the viewer unless an all-four-case completion manifest exists and each file's byte count/hash matches; it uses the existing local digital duck SVG helper (transitive `src/ui/duck-rig-view.mjs` → `src/core/duck-rig.mjs`) and actual position/time snapshots. The player and rival labels are P/A–E; rig colors are neutral placeholders, not claims of owned identities. Contacts get the same transient accent for actual participants under both models, no unselected severity scale; successful injury markers appear at recorded onset, finish list and seekable contact/injury list use recorded data. The viewer explains that examples were chosen after results and trajectories can diverge. A static event list and seek/still path provide non-moving access; reduced-motion settings never force playback. It is not a production UI or accessibility certification.

For eventual preview after root review, build an explicit task-owned static snapshot containing only the three viewer files, `injury-motion-gate.mjs`, `injury-motion-replay-output/{complete.json,four case JSON}`, `src/ui/duck-rig-view.mjs` and `src/core/duck-rig.mjs`; preserve repo-relative paths, verify source/snapshot hashes before and after copy. `injury-motion-static-server.py` serves a specified snapshot root on 127.0.0.1 with OS-assigned port and correct JS/MJS MIME, finite ≤85 s deadline, no repo root/owner data; run `python -I`, treat its process as owned by the finite capture runner, stop/wait in finally, record endpoint/readiness and actual cleanup. It is a bounded single-task helper, not a general service. Owner-facing interactive review needs a separately agreed lifetime; do not hand out an 85 s URL without explanation. Browser use requires root preview-lane assignment, isolated browser/profile, actual screenshots desktop and narrow, keyboard/pause/seek/static checks and content/time/participant inspection. The temporary lane pilot permits routine corrected validation within an approved stretch, not new seeds/provider calls/experiments.

## Proposed jobs and limits

After initial root review, use assigned compute lane: first `node --test injury-replay.test.mjs` (four pure tests; zero resolver calls), then exactly one `node injury-motion-replay.mjs` (four named calls max), both serial through unchanged bounded launcher with fresh host process/memory preflight (≥8 GiB available, no uncoordinated competing heavy job (the separately allocated Plan 58 lane is permitted)), `injury-motion-replay-pins.txt` and historical hashes verified; 1 GiB heap, 2 GiB sampled tree, 90 s per job, replay batch aggregate ≤90 s, output ≤8 MiB, no automatic repeat of experiment on failure or pin drift. A failing test may be materially corrected under the standing-lane pilot, but do not rerun a four-case race batch solely for a different outcome. Root reviews actual parity receipts before assigning preview lane. If parity fails, no `complete.json` and no viewer publication; saved-event timeline remains a limited fallback.

Outputs are report-local and cannot authorize production race, injury, save/replay, visuals, new odds, real student data or an effectiveness claim. Selected two seeds illustrate chosen patterns, not ordinary frequency or learner reaction. A report-local reviewer should inspect code and actual preview according to handoff; owner review remains separate.
