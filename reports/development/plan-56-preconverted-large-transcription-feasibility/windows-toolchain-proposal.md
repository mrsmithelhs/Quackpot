# Plan 56 Windows toolchain proposal — read-only comparison

2026-11-02. **Decision draft, not an installation or build authorization.** Upstream's documented Windows build uses clang-cl in a Visual Studio x64 developer environment, CMake/Ninja and Vulkan SDK; the distribution preset enables CPU variants and needs additional LLVM binary tools. A local-only fixed-baseline build can turn variants off and still uses the same upstream project and Vulkan backend. A portable CMake/Ninja distribution does not itself provide Windows headers, libraries, linker, resource compiler or a known-compatible C++23 compiler. No complete pre-existing supported toolchain was found in checked host paths. A portable LLVM/MinGW approach is not established by this investigation as a tested equivalent on this host; do not spend installation or build attempts on it implicitly. The scoped candidate is Microsoft's Build Tools with clang-cl and the Windows SDK, plus isolated CMake/Ninja and LunarG Vulkan SDK.

## Owner decision and acquisition evidence refinement

Root asks the owner whether they are willing to consider a **separately specified installation of Microsoft's shared Windows C++ development tools**. This machine-level step supplies the compiler, linker, Windows headers and resource tools that upstream's documented clang-cl build needs. Recommend Visual Studio 2022 Build Tools with the C++ workload and the explicit x64 toolset, Windows 11 SDK and clang components above; do not burden the owner with choosing individual compiler components. The exact frozen servicing version, dependency catalog, command, timeouts and resource supervisor remain a root-reviewed stage before any download or installation. Microsoft documents a [fixed-version Build Tools bootstrapper list](https://learn.microsoft.com/en-us/visualstudio/releases/2022/release-history), plus an offline layout with matching component selections and `--noweb` for the later installation. The bootstrapper can install/update the Visual Studio Installer; even obtaining an offline layout by running it is an executable action, not read-only research.

Microsoft's [system requirements](https://learn.microsoft.com/en-us/visualstudio/releases/2022/system-requirements) give **2.3–60 GB** free-space requirements across Build Tools configurations, not a measurement of this selected workload. Propose a conservative **100 GiB free on C: before acquisition/install**, a 60 GiB combined ceiling for newly attributable Microsoft install/cache/layout growth, 10 GiB for isolated source/tool/build work, and stop/return if C: free space falls below 30 GiB or the assigned ceiling/monitor fails. These are planning bounds, not measured package sizes; installation may write shared paths and sampled growth is not an enforceable instantaneous hard cap. Before execution root must review how shared-path growth is measured, stop/cleanup behavior, and installer update/elevation effects; if it cannot be controlled reliably, do not launch. C: had approximately 269.7 GiB free at the host inventory, which is transient. A model would require its own later disk and inference gate.

The 60 GiB ceiling is deliberately conservative; it is **not an estimate that this minimal configuration needs 60 GiB**. Available C: space establishes only point-in-time readiness, not authorization to consume the proposed budget. Final bounds and the actual install require separate clearance.
