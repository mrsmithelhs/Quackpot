# Plan 59 deterministic race arithmetic — bounded feasibility proposal

2026-11-05. **Proposal only.** QP Orch prefers a deterministic decision/evolution contract before portable production replay; neither this representation nor a source rewrite is approved. The current native-float kernel remains experimental, and the v1 resolver and historical replay validation remain unchanged. This protocol tests whether a candidate is viable; it does not adopt an accuracy tolerance, balance, save schema or production behavior.

## Candidate representation

Use a versioned integer state with JavaScript `BigInt` for every authoritative intermediate (not IEEE Number after a decision). Proposed units: distance and velocity **1,000,000 ticks per course unit and per course-unit/second**, acceleration 1,000,000 ticks per unit/s², time integer **microseconds**, angles unsigned integer **turns / 2³²** with signed shortest-difference in [-2³¹, 2³¹). A tick is exactly 50,000 µs. Represent rating, rest and Down factors as integer millionths; apply injury as exact rational 9/10 once, and affine conversion as `8.25 + rating/2` in fixed units. Initial limits: at most six participants, progress from -32 to 512 course units, lateral -6 to 6, speed 0–100 units/s, acceleration magnitude ≤20 units/s², and 800 ticks. These are proposed admission/overflow limits, not tuning or promises about real races. Define guard failure as unresolved before publishing any invalid boundary; reject malformed or out-of-range inputs, not clamp them into a race.

Use signed arbitrary-precision BigInt internally, with explicit checked input and intermediate magnitude caps (propose absolute 2¹²⁷−1 after each multiply/shift) even though BigInt itself will not overflow. All division uses one specified round-to-nearest, ties-to-even function, including signed values; zero is canonicalized, no NaN, infinity or negative zero. Cross products and squared distances are integer; `isqrt` uses a specified floor algorithm with bounded input/iteration. Serialize BigInt fields as canonical signed decimal strings (no plus sign, leading zero or `-0`), schema-tagged and bounded before parse; discrete enums, IDs, booleans, counters and ordered arrays have explicit field order. JSON numeric presentation views may be derived, but may not participate in mechanical decisions or the authoritative digest. No blanket increase to existing save/event limits is authorized.

## Angles and geometry

Prototype a fixed-iteration integer CORDIC rotation/vectoring implementation (e.g. 32 steps), with a committed, versioned table of integer `atan(2^-i)` turn constants and gain compensation derived once using an independently documented high-precision offline calculation. Runtime performs shifts/additions only, with explicitly defined signed shifts and quadrants; integer vectoring supplies heading/angle differences, and integer rotation supplies sine/cosine. The table bytes and implementation are part of the rules version. Do not generate tables with runtime `Math.sin`, `Math.cos` or `Math.atan2`; no network or new package is assumed. Test exact axis/quadrant behavior and near-wrap cases; compare against high-precision known vectors with a stated **measured** error envelope, not an unproved formal guarantee. If table provenance or a reliable reference cannot be established without adding a dependency, stop for a scoped tool/provenance decision.

Oval straight/bend centerline, tangent/normal, progress/lateral integration, heading turn caps, speed targets, braking, contact detection/impulse, correction bounds, crowd and Bounce eligibility, actual finish fraction and tie ordering all use the same integer representation. The discrete substep policy must specify how a fraction of a microsecond is represented or rounded, including the minimum progress step and a bounded no-progress outcome. For an initial comparison, retain the experimental discrete maximum relative travel per substep and stable pair order, but recompute the actual bound conservatively in integer arithmetic. Do not present it as exact continuous collision detection. Define collision, wall, opportunity and finish decisions on canonical pre/post states; no float-derived comparison may silently choose a branch. Test whether the integer course conversion can resolve selected finish/contact and corridor boundaries without forced movement or granting correction progress.

## Scoped experiment and source ownership

Request a separate **report-local, unmounted** feasibility turn for new files under `reports/development/plan-59-race-growth-injury-and-ability-integration/numeric-feasibility/`: `protocol.md`, `integer-math.mjs`, `cordic-constants.json`, `reference-vectors.json`, `decision-probe.mjs`, `integer-math.test.mjs` and exclusive result/receipt files. No game-owned module, existing PRNG, v1/v2 resolver, storage, schema or global payload limit is edited by this experiment. Freeze exact source/fixture/table hashes and runtime version per attempt. If creating the committed constants requires an unavailable high-precision facility, stop rather than substitute platform floating-point without disclosure. `BigInt` computation is exploratory; benchmark under a separate explicitly assigned modest lane, unchanged launcher and memory limits, finite no-watcher jobs, no provider, and no browser until a source-pinned browser comparison is separately cleared.

Initial probes should operate on fixed inputs and **not** claim a complete playable race: course-frame transforms across straight/bend joins; signed wall impulse and corridor boundary; contact/no-contact/grazing and occupied landing; actual finish before/at/after contact; injury/rest/Down before affine conversion; and keyed opportunity comparisons. Each probe records canonical inputs, branch decisions and outputs. Compare candidate integer outputs with high-precision reference vectors and the current v2 native result; a difference is a finding, not a reason to filter inputs or silently tune a constant. Include values just below/equal/above each branch threshold, equal crossing IDs/tie ordering, both signs, rounding halfway cases, maxima/overflow and malformed/oversized serialized fields.

## Falsifiers and decision gate

- Stop the candidate if integer error near a decision boundary can flip a selected rule without an explicit, reviewed tie/ambiguity policy, if contact correction can manufacture a finish, or if no reliable trig error bound and deterministic table provenance can be demonstrated.
- Stop if worst-case bounded work fails the existing resource envelope or the representative game cannot produce usable truthful results without repeated unresolvable guards. Report time, memory, caps and failed inputs, not just passing counts.
- Run independent same-input Node and isolated Chromium probes at pinned bytes only after a separately assigned browser lane; compare canonical serialized state, event/roll IDs, contact and injury decisions, crossing order and exact digest. Include deliberate tampering with seed, event, injury, crossing and material numerical state. A hash is integrity evidence against a trusted record, not cryptographic authentication against a malicious editor.
- Compare a finite explicit v1 reference on shared formulas and named inputs, with left-wall sign, multi-contact, tie and RNG differences disclosed; don't claim byte parity or reclassify historical v1. A few probes cannot certify all runtime/device combinations.

If these gates pass, return a quantified recommendation for root: exact rules/version and error envelope, demonstrated branch stability, resource cost, any experience differences, and whether a separately reviewed v2 production implementation is warranted. Root must also decide version dispatch, supported historical v1 replay/runtime, unsupported-save preservation and storage/transaction contracts before mounting. Failure remains useful evidence and may motivate a different bounded numeric design; no fallback to digest-only rounding is implied.
