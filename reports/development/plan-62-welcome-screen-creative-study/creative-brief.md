# Plan 62 — common creative brief for Sonnet and Flash

Status: prepared for both consultants; not yet dispatched. This is a request for creative advice, not an approved design or production specification.

## The experience

Quackpot is a browser game for a high-school game-design experience. Players inhabit an apartment and encounter a fictional duck-collecting gacha game; they later review a Receipt about their experience. The welcome should invite players into the **whole experience**, not look solely like an advertisement for the fictional gacha. Do not reveal the later narrative arc or put a manipulation-analysis lecture on the opening screen. It should feel appealing and coherent as a game, with space for ordinary apartment life as well as collectible-duck energy.

## Visual context

The accepted apartment kit is a layered, illustrated SVG environment with kitchen, living-room, bedroom and desk views. Its physical rubber duck is an inanimate object, not a living character; the separate digital collectible ducks can have their own motion. Reference candidates for actual visual input are the existing Plan 24 apartment gallery and current apartment art, identified in `flow-and-input-map.md`. Supply actual rendered references where the transport supports image input; a path in text alone is not evidence an image was seen. If images cannot be supplied, say so and use this text as limited context. Generated images are exploratory bitmap references, not production art or final controls.

## Already selected — preserve these

- A fresh run begins at welcome, then a short transition introduces the physical duck and an editable default name. Keeping the default is fine. Do not animate the physical duck as alive.
- Continue returns to a supported saved location and skips the introduction and naming. Settings and Credits pause presentation and dismiss back cleanly. Start and Continue do not wait for animation.
- Welcome offers Settings, Credits and manual usage download. After Receipt review, offer Start another run, Download usage file and View Receipt. Save/export semantics are existing system constraints, not a creative invention.
- Welcome and apartment music fade between one another; startup follows a user gesture and mute/static use works. Exact music, durations and visual treatment are open. Preserve the autosave preference; its placement and presentation are open. No duplicate kitchen onboarding.
- The game is local and static, with no runtime network, no forced waits, and an equivalent legible static/reduced-motion experience.

## Please propose

Give three meaningfully different compositions rather than three palettes for the same layout. For each, describe the visual hierarchy, how apartment and digital-game motifs coexist, likely desktop and narrow-screen adaptation, a brief transition to duck naming, restrained motion and an equivalent composed still, the character of a suitable existing MIDI-derived music passage, and the strongest tradeoff or failure mode. Explain what stays as real HTML controls rather than text baked into artwork. Include a practical proposal for where to expose the existing autosave choice without implying a changed default. Do not invent save retention, an ending, game mechanics, new audio rights or production commitments.

End with your recommended direction and two pointed questions that would help the owner choose. Be concrete enough for an image concept, but do not generate code or assume a design has been selected. No audio comprehension or new composition is requested.
