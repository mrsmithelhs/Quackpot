# Ren adapter notes — in progress, not mounted

Ren's current channel cannot be replaced by a projection of current state alone. `life52_social_intent` plus its validated effect/commit group owns social mutation; `social46_offer` may create `pending` without a display effect, and the older controller can initiate an offer while opening the channel. That open-created action is not evidence of a prior delivery. Keep the old route until an independent source transition or explicitly reviewed delivery rule covers creation.

| State | Display prerequisite and engine transition | Action boundaries |
|---|---|---|
| Pending uncommitted offer | `social46_offer_shown` records `social46_display` invitation/suggestion from authoritative plan ID, activity, intended day and current day. A changed/suggested or rescheduled plan requires a distinct new revision and fresh shown fact. | `social46_reply` accept/decline/reschedule, `social46_suggest_activity`; engine requires shown, validates ID and slot. Reproject after each successful transaction; operation ID and expected log length are fresh. |
| Committed plan | `social46_ack_shown` records accepted text; when seating unconfirmed, `social46_floor_shown` precedes confirmation. | Cancel, reschedule, floor confirmation and door arrival remain separate engine actions with their own schedule rules. |
| Response and reply | `social46_response_shown`; a chosen response creates a reply requiring `social46_response_reply_shown`. | `social46_response_reply` and `social46_response_dismiss` are gated by actual shown state; do not infer a read from a response or vice versa. |
| Door / introduction / active scene | Door and scene have their own shown/choice/arrival lifecycle and are not historical Messages. | Keep existing door/scene and no pre-introduction relationship. |

Proposed next seam: derive a bounded current message identity/revision from the replay-validated creation or change transaction and exact source plan/response ID; register it at the transaction commit, outside its atomic effect group. Every revision must be validated against reconstructed life at that exact prefix, supersede earlier actionable revisions and survive canceled/dismissed/expired states without an action. Then route visible-content acknowledgment through the matching existing source shown operation before a separate read event; refresh the view with fresh state and use `applyFiveSlotSocialAction` with new operation ID and current expected log length on each choice. This is a design sketch until all variants and prefix transitions are implemented and tested. `ren-channel-view.mjs` stays authoritative in the meantime. No source event has been added for Ren by this note.

## Historical transitional explicit contact bridge

The current opt-in slice exposes a read-free system contact only after `introShown` and, for revision 2, `intro.numberShared`. Choosing **Open contact** deliberately invokes the existing `onSocialOpen` source operation, then hands off to the existing Ren channel; passive inbox/thread inspection creates no offer. That operation retains the existing initiator, activity/day and once-per-day rules. This is a bridge, not the requested completed Ren projection: the old channel still owns shown callbacks and all actions, and the desk-phone route is not yet replaced. The eventual adapter must transfer those facts and checks to the global thread before removing the old channel. A natural unsolicited-delivery cadence remains an unselected future question, not an added scheduler.
