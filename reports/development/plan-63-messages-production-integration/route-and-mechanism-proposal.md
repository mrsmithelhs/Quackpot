## Proposed identity, delivery and action model

1. Pure projection derives communications only from current authoritative event/state facts, with no RNG. Use fixed namespace thread IDs (`work`, `ren`, `loan`, `launch`, and fixed history IDs). Each adapter supplies an immutable logical message ID from its actual underlying offer/plan/loan ID and message kind. A delivery ID is source event sequence or a deterministic source-owned occurrence key; a revision is a versioned canonical content/fact key, not a render count or balance rerender. Historical IDs are fixed, pre-read and never arrival events. Identical adapter outputs deduplicate by delivery/revision; a changed actionable fact creates a revision only when the source actually establishes a new communication, not merely when cash changes. Adapter-specific keys and valid transition tables must be agreed during the source turn; no fabricated historical delivery sequence.
2. Order real deliveries by their original append sequence or deterministic authoritative schedule occurrence, with a fixed ID tie-breaker; static history sorts behind actual deliveries in authored order. A projected current fact with no established delivery is not silently advertised as an incoming message: retain its existing route or define an explicit delivery event at the existing source transition first. Thread unread means at least one delivered, unacknowledged revision, independent of current action eligibility.
3. At Decide opening and again at confirmation, resolve the message's source identifier against current engine state and obtain fresh authoritative proposal/terms. Existing engine operations, current revision/log guards and idempotency IDs perform the transaction. Stale, resolved or expired choices become informational with a clear refreshed result; they never silently execute. Dismissal/read never answers, changes a deadline, spends time or pays. Do not place arbitrary callback data or balances in persisted message metadata.

## Proposed display, state and replay contract

- Persist bounded versioned message acknowledgments as validated append-only `message_read` events, keyed by exact delivered ID and revision, outside atomic transactions and before terminal only. Reconstruct read state from validated log, rather than creating a second unverified authority. Deduplicate against log before appending; enforce a fixed registry, per-ID syntax/length and bounded cardinality, and reject unknown, future, duplicate or undelivered revisions during replay. Payload has IDs/version only, no arbitrary text, balances or user data. Exact caps and adapter registries must be pinned with implementation and reviewed against supported save limits. Existing schema-6 dispatch/envelope and unsupported-save preservation stay intact; **no independent schema cutover**. Root and Plan59 must decide how schema-6 replay identifies the new optional message policy and handles pre-feature schema-6 saves without mutating historical semantics.
- Only after successful mounted conversation, visible document, uncovered active layer, and a currently connected target intersects its scroll viewport and visual viewport should a deferred acknowledgment be attempted; require the message content target, not inbox row, and recheck exact ID/revision and geometry at callback time. A keyboard or screen-reader user can focus an explicitly labelled message content target, which scrolls it into view; focus alone on an offscreen or covered node does not acknowledge it. No timer or perception claim. If layout/visibility cannot be established, mount fails, document is hidden, the layer is covered or revision changes, keep unread and retry when valid. Disconnect observers on close/unmount. This is a proposed operational display threshold, not proof that a person perceived content or complete occlusion detection.
- For actual promotion/offer content, invoke the existing source-specific shown operation only at qualifying content visibility, before enabling a response that requires it; record the existing `offer_shown`/`cue_shown` payload so Receipt continues to project actual displayed evidence even if no action follows. Preserve Ren's corresponding source-specific shown transaction. Ensure one idempotent shown record per existing semantic occurrence, no duplicate Receipt claims, and no injected events between intent/effects/commit or terminal/Receipt. A failed save surfaces existing storage warnings; in-memory read never implies durable success. Reopen/reload derives only verified committed state. Avoid mechanics RNG on all navigation.
