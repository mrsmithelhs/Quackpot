## First question: preserve history and allow normal restart

Recommend a separate versioned profile history, with one opaque random ID per run, separate from the single resumable save. Before a confirmed restart can replace the current supported save, durably merge the available old-run projection and recorded unlocks, verify the history write, then replace the save with the new run. Normal autosave and manual Save operate on that new run thereafter. Cancel does neither write and keeps View Receipt. If history cannot be persisted, refuse replacement and keep the Receipt available; do not silently trade history for a new save. The new run can only be called saved after its save write is verified. Autosave off retains the old save until manual Save or autosave is enabled; archive the old evidence before leaving the Receipt and recheck the old primary at the later replacement.

This requires a concurrency change: the existing localStorage comparison and write are not atomic. Recommended initial schema5 policy is a same-origin Web Lock, held across read/validate, history merge, readback and save replacement; all participating save, clear and history writers must use that same lock. Re-read the actual primary inside the lock, compare its exact bytes with the user's confirmed snapshot, and refuse on a mismatch. Hold the lock only for bounded local operations, never across a dialog. Where the lock API is unavailable or denied, fail closed for destructive replacement and offer an explanation; do not claim safe cross-tab replacement. Existing tabs running older code, developer tools, storage eviction and unrelated same-origin scripts do not cooperate, so this is not a universal atomic CAS or protection against arbitrary writers. Root must determine whether that limitation and required shared-writer refactor are acceptable. Schema6 development storage stays separate and requires a distinct decision; do not imply coverage.

### Proposed write and recovery protocol

1. At run creation generate a cryptographically random ID and persist it with the save envelope. A supported pre-feature save needs a once-only binding: under the lock validate its exact bytes, assign an ID and durably associate that ID with its exact save identity before exporting or replacing it. Preserve the binding across subsequent saves; use an explicit versioned save metadata extension subject to validation/replay review. Do not use a seed, name, timestamp, fingerprint exposed in ZIP, or an installation ID as the run ID. Never assign a fresh ID on each export. If a safe binding cannot be persisted, report unavailable rather than invent identity. Review compatibility of the metadata change before implementation.
2. Prepare a bounded allowlisted projection from the live engine log, and separately from any different supported saved run that would be displaced. In particular an autosave-off terminal run and the older resumable run can be distinct; archive both with their own IDs. Bind and persist identities before accepting replacement. Merge only exact matching IDs and comparable append-only prefixes; identical snapshot is a no-op, a verified extension replaces its earlier projection, divergent histories are retained as a conflict and block destructive replacement rather than silently choosing one. Do not infer identity from equal summaries.
3. Under the lock, re-read primary and history; validate version, capacity, integrity and expected primary. Write a single serialized history value and read it back, then recheck primary and write/read back the candidate save. Only then switch the live engine to the candidate. Keep the current Receipt/old primary on refused or failed pre-save steps. Do not roll back over bytes that may belong to another writer. If the save write's outcome cannot be read, report uncertainty and require reload/reinspection, not a false success or preservation guarantee.
4. Crash after archive but before replacement leaves the old save and an idempotent history record; retry merges by ID. Crash after replacement leaves archived old evidence and the new save, subject to browser durability/eviction. A failed or interrupted history write blocks replacement; quota/unavailable storage must show a useful message and retry. Never evict older records silently. A failed new save can leave an extra valid archived snapshot; retry is idempotent. Use single-key atomicity only as provided by the browser; no promise of physical disk flush or cross-key transaction.
5. Invalid, corrupt or future-version history is preserved untouched and export/replacement is refused with recovery guidance, not reset. Corrupt/unsupported saves retain current explicit backup/temporary/reset safeguards and are not projected as valid. Clearing the browser or origin can erase both stores, and this cannot be detected retroactively. Explicit in-app history clearing should require separate confirmation, explain that it does not clear Continue, and record no identifying marker after a full site-data clear. Clearing only a save must archive supported evidence first or explicitly disclose unrecorded loss if no evidence is recoverable. Do not automatically clear history on Uninstall, restart, or save reset.

## Proposed package and limits

One student-initiated local download, genuine ZIP with exactly one root UTF-8 `usage.json`; separately version format, history schema, export schema and event/achievement catalogs. Suggested envelope: `{format, schemaVersion, catalogVersion, coverage, runs, achievements}`. Each run has opaque `runId`, status (unfinished/terminal/unknown), evidence completeness and reasons, nullable summary counts, timeline coverage and ordered allowlisted events. Preserve original event sequence and gaps; distinguish displayed, action, committed and revealed evidence and recorded odds. A reveal represented in a truncated timeline must retain its referenced commitment. No raw payload copying, whole saves, free text, names, reflection, seed, exact time or profile ID. Profile coverage must state that pre-feature, cleared, other-device, unsaved, unsupported or failed-storage data may be missing; only claim specific observed gaps when known. Empty history differs from unavailable/corrupt history.

Export merges a supported current save and live run only after stable identity and durable recording succeed, then emits each ID once in deterministic order. Exact duplicate snapshots collapse; valid later prefix extension supersedes older; conflicting same-ID histories are refused/flagged, not double-counted. No identity or authenticity claims: a run ID is linkable, CRC detects corruption, and multiple profiles/people cannot be resolved from a package. Repeated exports carry the same run IDs.

Reuse Plan42's one-member ZIP and version refusal, not its synthetic schema as production. Starting ceilings: 8 MiB archive, 2 MiB actual JSON, 2,000 timeline events across the entire package, depth 12, strings 512 UTF-16 units; bound run count and local history separately (recommend 100 records and 2 MiB serialized history as initial proposal). Exact run/event limits and truncation policy need owner/root approval. Never silently discard a run to fit: refuse with explanation when all records cannot fit; allow bounded timeline truncation only with explicit per-run omission/coverage counts and self-contained references. Capacity is not a browser quota guarantee. Plan42's 20-file/32 MiB compressed and 16 MiB expanded batch limits concern a future importer, not one export. Independently decode a synthetic package with a tool that supports the exact output or demonstrate explicit version refusal.

Plan42's tested dependency is `@zip.js/zip.js` 2.18.0, BSD-3-Clause, tarball integrity `sha512-xv0lRTXFZQkDu88HkxXY4FfHEVfhA+KzxOARye0kDBZvylP1tJ15v99qiTq1Mm30WxakxKIySk9uVVrwSXkdZA==`; its report-local modified reader/worker is not a production dependency. This proposal does not authorize acquisition or assert existing production integration.
