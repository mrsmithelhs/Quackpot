## Writer inventory and lock contract

One origin-scoped named exclusive Web Lock guards all schema5 primary, backup, run-identity binding and history mutations. `src/main.js` currently invokes: (1) `maybeAutosave` → `saveGame`, including the many gameplay callbacks and `enterLife`; (2) Settings `saveNow`, including the autosave-toggle-off write; (3) `startAfterReceipt` → `replaceRestartSnapshot` and `savePendingRestart` on later Save/auto enable; (4) unsupported-development explicit replacement → `replaceUnsupportedSave`, and backup → `backupUnsupportedRenSave`; (5) corrupt-load and failed-hydration dialogs → `clearGame` or `backupCorruptSave`; and (6) schema6 Receipt clear, which is separate and excluded. `storage.mjs` itself writes/removes primary and backup in these helpers; `restart-storage.mjs` writes primary. New archive, identity and explicit history clear are additional writers. No other production `STORAGE_KEY`, `saveGame`, `clearGame`, backup or restart writer was found by `rg` across `src` excluding tests; re-audit at turn handoff. Schema6 has independent keys and remains out of coverage. Browser clearing, old versions and other scripts are noncooperating and cannot be locked by this version.

Route every listed schema5 mutation through one coordinator; do not leave callable direct production bypasses. Backup reads/copies and unsupported/corrupt reset must acquire the same lock and verify the expected primary and existing backup immediately before mutation. Preserve the unsupported preservation path; do not invent a valid history from unsupported/corrupt bytes. A destructive corrupt/unsupported reset requires explicit existing confirmation plus an accurate disclosure that its evidence is unavailable; corrupt data is never parsed into the history. `clearGame` currently swallows deletion errors: replace that behavior in these paths with verified success/failure without erasing backup or history by accident. Explicit history clear under lock removes only history and identity association, not primary/backup, with confirmation and readback; the current save may later be recorded anew and its ID must remain stable. Clearing history cannot prevent other tabs from re-archiving a run: notify/invalidate active tabs using a history-generation change under the lock, and refuse stale queued writes until reinspection; browser full-site clearing is still undetectable retroactively.

Use a per-tab serialized, ordered async queue and one coordinator for mutating operations. Each operation captures the relevant engine/session generation and expected raw primary; after lock acquisition recheck both generation and bytes, and discard stale queued snapshots. Never let a delayed autosave from a previous run overwrite a later restart. Serialize/coalesce only compatible same-run saves without reversing event order; cancellation, view changes and manual Save need explicit completion/error handling. Do not hold the lock while waiting for confirmation, DOM rendering, worker compression, user action or network. A bounded lock acquisition may time out and report failure; never use `steal`. Make Settings await the actual result rather than treating a Promise as synchronous success. End-of-run UI is immediately reachable: archive asynchronously with a visible pending/failure state, not an enforced wait or a barrier to Uninstall/Receipt.

**No lock available/denied/timeout:** Continue may read and validate an existing primary and display a run, with an honest warning that save and history recording are unavailable; it performs no metadata binding or durable writes. Ordinary autosave and Save also refuse durable mutation, retain current play in memory and show unsaved status. Do not silently fall back to unsafe direct writes. Restart replacement, deferred first save of a replacement, explicit clear, backup/reset and archive/export requiring a write fail closed, preserving current visible Receipt or play state. Retry after the lock is available rechecks bytes and generation; an export must not report a successfully captured live run if its archive failed. A local read-only export of already validated committed history could be a later independent feature, not assumed here. These choices are deliberately more conservative than Plan64's current best effort and need root acceptance.

## Identity, committed evidence and truncation

`GameEngine.toEnvelope`/`fromEnvelope` currently serialize schema5 without a run ID; `savedAt` changes on every serialization and is unsuitable for identity. Add a versioned opaque random run ID in schema5 envelope metadata, validated and round-tripped by `src/core/game-engine.mjs` and `src/core/storage.mjs`; do not touch deterministic RNG or add a player-facing ID. For a supported pre-feature save without ID, lock, compare exact original primary, validate, insert ID into a copy preserving game state/log/RNG, validate and write/read back that new envelope before an archive or first mutation. If interrupted before write the original is unchanged; after write future reload sees the same ID. Never use a synthetic ID derived from timestamp, seed, name or weak event hash. A purely in-memory new run receives its ID once at creation; archive stores it before departure, and later save includes it. Two distinct runs, including a saved older run and a terminal temporary run, retain separate IDs. If legacy binding or write verification fails, do not assert durable identity or replace.

The event log's existing FNV chain is a useful integrity check but is not collision-resistant proof of prefix equality. Store **separate bounded comparison commitments**, not the truncated exported timeline: for each archived run, retain source-entry count and SHA-256 digest of canonical complete source-log prefix bytes, with canonicalization and version specified in code and test vectors. On a candidate with at least that count, recompute the digest over exactly the old prefix and compare; equal counts/digest are the same snapshot, longer matching prefix is a permissible extension, and shorter matching prefix never replaces the longer record. A mismatch is a conflict, including a branch from the same saved run in another tab; preserve the previously committed record, report the conflict and block replacement/export that would silently choose either branch. Cryptographic digests are probabilistic collision resistance, not authentication. Hashes and any comparison metadata stay local and out of `usage.json`; source logs, free text, names, seeds, exact timestamps and entire saves are not history/export fields. Raw log processing is transient and bounded, never copied wholesale to the history. Size/time limits and UTF-8 canonical encoding are mandatory; exceeding them is an explicit failure, not a partial digest. This lets the timeline be truncated independently while still testing prefix continuity. Compression/JSON generation cannot silently reduce recorded totals or erase a run.

One caveat needs root disposition: a digest proves equality only for the source prefix being compared; it cannot reconstruct omitted events or establish that a browser never lost earlier data. History must store its selected allowlisted timeline and original coverage/omission counts; once omitted, data is not claimed recoverable. A later extended source log can rebuild a fuller projection while the source is available. Fail on a projection that cannot fit rather than truncating the internal comparison commitment or silently erasing earlier evidence.

## Ending, autosave off, interruption and explicit clearing

After a terminal event, enqueue an archive of the current in-memory source independently of autosave; after `recordReceiptPresented` append/merge the later Receipt snapshot. Preserve event ordering, and keep the Receipt visible whether archival succeeds or fails. Show status and a retry action at Receipt/Welcome when archival is pending or fails. At confirmed restart, re-archive the latest terminal memory and any distinct supported primary under the same lock before displacement; with autosave off, retain the primary until later manual Save or autosave enable and repeat the same guarded check at that later write. Cancel writes no restart candidate and leaves Receipt reachable. Archiving may already have occurred at ending/Receipt before Cancel; do not describe Cancel as undoing those earlier history writes.

On abrupt tab close, crash or browser kill, do not depend on `beforeunload`, a prompt, asynchronous close handler or a final write: only last verified history and save survive subject to browser storage durability. If closure occurs before the queued ending/Receipt archive commits, its unsaved tail is lost, and a future export cannot prove it existed. Disclose up front that history records at these boundaries even when autosave is off, while unsaved progress can still be lost on closing. On failure retain live evidence in memory, explain it is at risk and allow retry or export once a durable archive succeeds; do not force continued gameplay. Clearing history requires a distinct explicit action and does not erase the playable save; say the currently saved run may be recorded again, and past cleared or prior-to-feature data cannot be recovered or counted.
