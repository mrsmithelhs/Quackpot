# Proposed first-wave sequence

**Date:** 2026-10-23
**Status:** proposal awaiting owner approval. All seven packet frontmatter statuses remain `draft`; no implementation assignment or tuning decision is made by this document.

## Recommendation

1. **Plan 01 — seeded economy and Receipt simulation first.** Use the Tuning starting table as an unchanged baseline, then bounded sweeps and adversarial traces for S1–S4. Its findings recommend values; the owner decides what, if anything, becomes a rule.
2. **Plan 02 — Vite/static Pages spike beside Plan 01, or immediately after it.** Keep write scopes disjoint. Prove a local build and subpath behavior, then send the folder-layout recommendation to the owner. Live Pages publication or remote configuration requires separate owner approval. Never publish from `docs/`.
3. **Plan 03 — mechanism slice after Plans 01 and 02 are reviewed and complete.** Before coding, have the owner select the one trade-off and approve its event/log/save wiring. Demonstrate Uninstall, retention offer, local save/resume and an honest Receipt in a played route. A later owner play review decides whether the mechanism works.
4. **Plan 04 — small SVG rig and synthesized-sound spike after the layout decision.** It can run beside Plan 03 only with disjoint files. Show one composable sample and one local sound before wider production.
5. **Plans 05–07 — independent investigations.** Fatigue and the pre-race choice, optional odds detail, and run-usage export/teacher analyzer each return a recommendation to the owner. They may run while the foundation work proceeds, but none changes game policy or implementation until its owner gate is resolved. Plan 07 may inspect BrowserBattlegorithms read-only as authorized.

## Why this order

The numerical model tests whether the squeeze, pity and duplicate economy can work without per-variant tuning. The build spike prevents UI work from assuming an unratified layout. Their accepted results bound the first playable mechanism. Art/audio can be proven separately, and the three open design items remain investigations rather than silent features.

## Gates to preserve

- Owner approval of this sequence comes **before** promoting any packet from `draft` or assigning an implementer.
- `plan-status.js check <id>` must pass before any packet begins. A draft packet will fail by design.
- Plans 01–04 each require a concrete mechanism or layout outline before significant structural work; their packets specify the stop point.
- Owner acceptance of simulation values, folder layout, fatigue behavior, odds detail, and export/analyzer fields is separate from an implementer's report or passing tests.
- Public deployment, remote configuration and push require explicit owner authorization with the proposed settings/artifact visible.
