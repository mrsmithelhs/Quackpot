## Questions the review must address

1. **Historical causation.** Is the perceived regression pattern supported, contradicted or mixed? Trace representative original production → prototype → owner selection → synthesis/packet → integration → verification → repair. Identify where meaning or behavior changed, including orchestration errors, ambiguous owner approval and rushed scope amendments. Separate intentional changed direction from unintended regression; distinguish later discoveries from what the original implementer could reasonably know. Include a successful comparison and competing explanations.

2. **Approval and prototype provenance.** How can an integrator distinguish selected new behavior from faithful context, placeholder surroundings and intentional omissions? Inspect whether qualifications vanish across ledgers/summaries/handoffs. What should accompany an approved preview so an agent doesn't treat every pixel/button as gospel? Recommend concrete, lightweight artifacts or mechanisms and show how they'd apply to a real case; don't merely prescribe more prose.

3. **Behavioral modularity.** Map rules, orchestration, presentation, content, animation, assets, saves, RNG, event evidence and Receipt projection. Identify coupling that increases the actual change footprint, not simply long files. Can a feature change without replacing adjacent UI/navigation, duplicate outcomes, global CSS effects or a second state machine? Which boundaries are healthy and should be retained? Quantify with concrete representative change paths where useful; line counts/import counts are signals, not quality verdicts.

4. **Focused production-faithful review.** Distinguish exploratory prototype, art gallery, production checkpoint and controlled component harness. Can owner/agents reach the actual feature without replaying the entire game or recreating a second simplified game? Assess current checkpoint coverage, reachability/freshness, lifecycle realism, compatibility and privacy. Which surrounding capabilities (Settings, Uninstall, saving, navigation, motion) must remain real for a focused preview to be trustworthy? Worktrees may help writer isolation but don't by themselves prove preview fidelity.

5. **Preservation contracts and integration scope.** How should a packet identify existing behavior the change must preserve, exact replacement seams and selected additions? Find where an integration silently replaced a whole surface to add one feature. Propose an affordable way to discover/preserve neighboring behavior, including accessible focus/copy/reduced motion; avoid a universal giant checklist. Distinguish visual acceptance from exact mechanics/source ownership.

6. **Verification quality.** For actual historical regressions, which checks would have failed, and which passed while asserting the wrong interpretation? Examine real wiring, return/reload, alternate states, adjacent features, fixture freshness and reachable traces. Look for tests rewritten to endorse a regression, without assuming bad intent. Recommend a small number of high-yield checks/negative controls with demonstrated value, not generic coverage targets or more mirrored implementation tests.

7. **Parallel development.** Separate file ownership from semantic ownership of phases/phone context/HP/save/event contracts. Where are disjoint-file plans still conflicting? Which production work can run concurrently, which can only design concurrently, which requires serialized writes, and how should changes to a shared contract reach active packets? Evaluate integration debt, source-map drift and active-branch assumptions as alternatives to pure code defects. No presumption that more agents or worktrees solve semantic conflicts.

8. **Future fitness.** Walk several actual upcoming features through the present architecture, especially work/gigs, Ren, weather/audio transitions and late disorientation. Show required touchpoints, appropriate versus avoidable coupling, and whether a shared seam should precede several upcoming packets. Preserve the static/offline/local-data/Receipt honesty constraints. Prioritize realistically; no framework migration or rewrite merely because the project has grown.
